OSNTC.045 explains a networking challenge in GPU training clusters: an Ethernet link can remain up at 400G or 800G while RDMA traffic slows or stalls under congestion. RoCEv2, short for RDMA over Converged Ethernet version 2, can move data efficiently between compute nodes without traditional CPU-driven copies for every operation. Reliable performance requires attention to flow control and buffering, not merely physical link status. Begin with OSNTC.044 on optics and FEC and the RDMA introduction.

PFC, ECN, and DCQCN do different jobs

Priority Flow Control (PFC) is hop-by-hop. A congested receiver can send a pause request for an identified traffic priority to its upstream neighbor. Protecting a full queue can reduce packet drops, yet excessive pauses can spread congestion, delay unrelated flows sharing that priority, or cause head-of-line blocking. PFC is not an end-to-end application rate controller. Explicit Congestion Notification (ECN) marks eligible packets in their IP headers to signal congestion before switches would otherwise discard them. An ECN mark alone does not automatically reduce traffic.

Data Center Quantized Congestion Notification (DCQCN) provides rate feedback. When a RoCEv2 receiver detects ECN-marked traffic, it can generate a Congestion Notification Packet (CNP). The compatible sender uses that signal to adjust its sending rate. In many validated lossless Ethernet designs, ECN/DCQCN manages congestion proactively while PFC protects queues during bursts. NVIDIA's congestion-control explanation and Cisco's AI networking blueprint discuss the interaction.

Check the traffic class and both endpoints

Inspect the RDMA traffic priority, DSCP or PCP mapping, host adapter settings, queue classification and buffer policy across the intended network path. A priority mismatch can place a flow in the wrong queue or pause a class that should remain best-effort. A vendor example may use UDP destination port 4791 for RoCEv2, but its traffic-priority assignment is platform-specific. NVIDIA's Onyx RoCE command reference shows configuration examples, not settings suitable for indiscriminate copying.

Physical checks remain necessary. Low optical receive power, FEC uncorrectables or incorrect breakout lanes can create loss without queue congestion. Use OSNTC.041 on FEC errors and OSNTC.043 on breakout mapping to separate an optical fault from a traffic-management problem.

Gather read-only evidence before changing anything

On supported NVIDIA Cumulus Linux versions, the official RoCE guide documents commands for viewing RoCE QoS and interface counters. The examples below are not Cisco NX-OS commands and can vary with the release or hardware. They inspect state rather than altering it.

nv show qos roce
nv show interface swp16 qos roce status
nv show interface swp16 qos roce counters

Record the interface, traffic priority, snapshot time, PFC pause packets and pause duration where available. Add ECN-marked packets, CNP packets, queue occupancy, buffer drops, NIC health and application throughput. Compare increments over the same observation interval rather than treating lifetime counters as current rates. Do not reset counters before collecting evidence. Cisco also documents the read-only show interface priority-flow-control family for supported Nexus releases.

Diagnose a hypothetical pause storm

Assume a fictional cluster leaf sees received PFC pause frames increase from 120 to 420 over five minutes, while a GPU workload slows. The difference is 300 frames, averaging 60 additional pause frames per minute. The example cannot establish total pause duration or prove which component caused the congestion. Examine actual pause time, buffer pressure, ECN/CNP feedback and slow-receiver counters. An interface reset or a wrapped counter would also invalidate simple subtraction.

If ECN marks increase without a sender rate response, confirm the receiver, CNP feedback path and adapter congestion-control support. If pauses spread across adjacent ports, inspect the blocked receiver and queue isolation. If FEC errors rise at the same time, investigate the optical path. Also compare active paths against OSNTC.020 on load balancing and LACP. A congested path can coexist with spare capacity elsewhere.

Verify repairs using a matched workload

An approved fix might involve classification, queue scheduling, ECN thresholds, host configuration, load balancing or defective hardware. Never change production PFC settings merely to see whether a link stays up. Obtain a change window, review the vendor's validated design, and preserve a rollback option. Compare latency, throughput, ECN marks, pauses, drops and application progress under the same workload before and after any authorized modification. Some supported architectures use resilient or ECN-centered RoCE policies instead of identical PFC behavior, so no single configuration applies everywhere.

Practice: Write an incident ticket for the fictional five-minute sample. Label observations, possible causes, next read-only tests and measurable conditions for closure. Avoid calling the link healthy solely because the carrier remains up.
