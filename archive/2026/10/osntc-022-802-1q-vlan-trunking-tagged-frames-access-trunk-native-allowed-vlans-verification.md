<!-- wp:paragraph --><p>A virtual local area network (VLAN) separates one physical Ethernet switching environment into multiple logical Layer 2 networks. An access port normally carries traffic for one VLAN, while a trunk port can carry traffic for multiple VLANs across the same physical link. IEEE 802.1Q provides the standard tagging method used to identify which VLAN a frame belongs to as it crosses a trunk. This lesson follows <a href="https://bitcoinversus.tech/2026/10/09/osntc-021-troubleshooting-switch-ports-link-status-errors-vlans/">OSNTC.021: Troubleshooting Switch Ports</a> and builds directly on <a href="https://bitcoinversus.tech/2026/09/30/osntc-004-vlan-basics/">OSNTC.004: VLAN Basics</a> and <a href="https://bitcoinversus.tech/2026/10/02/osntc-008-ethernet-frame-basics/">OSNTC.008: Ethernet Frame Basics</a>.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">ELEMENTARY OVERVIEW</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Imagine two switches that both contain VLAN 10 and VLAN 20. Without trunking, a separate physical cable could be required for each VLAN between the switches. A trunk solves this scaling problem by carrying traffic for multiple VLANs over one Ethernet link. The switches distinguish the traffic by adding an IEEE 802.1Q VLAN tag to frames that cross the trunk.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>An access port and a trunk port therefore serve different purposes. An access port usually connects an endpoint such as a workstation, printer, camera, server, or miner and normally associates untagged endpoint traffic with one VLAN. A trunk port usually connects networking devices such as switches, routers, firewalls, hypervisors, or access points and can transport several VLANs over the same link.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">LEARNING OBJECTIVES</h2><!-- /wp:heading -->

<!-- wp:heading --><h2 class="wp-block-heading">WHAT IEEE 802.1Q ADDS TO AN ETHERNET FRAME</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>IEEE 802.1Q inserts a four-byte tag into an Ethernet frame so that a receiving bridge or switch can identify the frame's VLAN membership. The standard is part of the broader IEEE 802.1Q bridge and VLAN specification. IEEE lists IEEE 802.1Q-2022 as the active published standard for bridges and bridged networks, including VLAN operation and management.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>The tag contains information that includes a 12-bit VLAN identifier. Twelve bits provide values from 0 through 4095, although not every value is available as a normal user VLAN. In common enterprise switching, VLAN IDs 1 through 4094 are the familiar configurable range. The tag also contains priority information used for Layer 2 quality-of-service behavior.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>A switch forwarding a frame from an access port into a trunk associates that frame with the access VLAN and, when required, inserts the appropriate 802.1Q tag before transmission. The receiving switch reads the tag, keeps the frame inside the correct VLAN, and removes the tag when forwarding the traffic out a normal access port toward an endpoint.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">ACCESS PORTS VS. TRUNK PORTS</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>An access port normally belongs to one access VLAN. For example, switch port Gi1/0/12 might be an access port in VLAN 20. A workstation connected to that port does not need to know that VLAN 20 exists; the switch performs the VLAN association.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>A trunk port carries multiple VLANs. For example, an uplink between two switches could transport VLANs 10, 20, and 30. Rather than dedicating three physical cables to those VLANs, one trunk link transports all three while tags keep their Layer 2 broadcast domains logically separate.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">THE NATIVE VLAN</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>On an IEEE 802.1Q trunk, one VLAN may be designated as the native VLAN. In common Cisco switching behavior, native-VLAN traffic can cross the trunk untagged. Both ends of the trunk should agree on the native VLAN. Cisco documentation warns that native-VLAN mismatches can cause incorrect forwarding behavior and can contribute to spanning-tree problems.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>A technician should never change a production native VLAN casually. First verify both ends of the link, the intended design, the spanning-tree state, and any connected non-Cisco equipment. A mismatch should be treated as a configuration fault that must be corrected deliberately on the appropriate interfaces.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">ALLOWED VLANS</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>A trunk does not have to carry every VLAN configured on a switch. An allowed-VLAN list limits which VLANs may cross the trunk. Restricting the trunk can reduce unnecessary broadcast propagation and makes the intended Layer 2 topology easier to understand and troubleshoot.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>For example, if an uplink only needs VLANs 10, 20, and 30, a technician can configure those VLANs as the permitted set rather than carrying unrelated VLANs. Before removing a VLAN from an existing trunk, verify that no downstream device depends on it. An incorrect allowed list can create a failure in which the physical link remains up but one or more VLANs lose connectivity.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">COMMON CISCO IOS-STYLE CONFIGURATION</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>On many Cisco IOS-style switches, a technician enters interface configuration mode and uses <code>switchport mode trunk</code> to place the interface into static trunk mode. An allowed list can be configured with <code>switchport trunk allowed vlan 10,20,30</code>. A native VLAN can be set with <code>switchport trunk native vlan 99</code>. Exact syntax and defaults vary by switch model, software release, and vendor, so production changes should always be checked against the platform documentation.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Cisco's trunking documentation describes 802.1Q as a method for carrying several VLANs over a point-to-point link and shows verification with commands such as <code>show interfaces trunk</code> and <code>show interfaces interface-id switchport</code>. The same documentation explains that 802.1Q inserts a four-byte tag to identify VLAN membership.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">VERIFY BEFORE TROUBLESHOOTING</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Start with read-only verification. <code>show interfaces trunk</code> can display interfaces that are trunking, their encapsulation, native VLAN, and allowed VLANs. <code>show interfaces Gi1/0/24 switchport</code> can show administrative and operational switchport mode. <code>show vlan brief</code> helps confirm that the VLAN exists locally. <code>show spanning-tree vlan 20</code> helps determine whether spanning tree is forwarding or blocking a path for that VLAN.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Always compare both ends of a trunk. A technician should confirm that both ports are operationally up, both are intended to trunk, the relevant VLAN exists on both switches, the VLAN is permitted on the trunk, native VLAN settings agree, and spanning tree is not intentionally blocking the path. If the trunk is part of an EtherChannel, troubleshoot the logical port channel and its member links together; review <a href="https://bitcoinversus.tech/2026/10/08/osntc-020-link-aggregation-lacp-etherchannel-port-channels-member-links-load-balancing-failure-recovery/">OSNTC.020: Link Aggregation and LACP</a>.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">COMMON FAILURE PATTERNS</h2><!-- /wp:heading -->
<!-- wp:list --><ul><li><strong>Physical link up, one VLAN down:</strong> check the allowed-VLAN list and whether the VLAN exists on both switches.</li><li><strong>All trunked VLANs down:</strong> verify that both sides are actually trunking and that the correct physical ports are connected.</li><li><strong>Native VLAN mismatch:</strong> compare the native VLAN on both sides and correct the design deliberately.</li><li><strong>Unexpected blocking:</strong> inspect spanning-tree state before changing trunk settings; review <a href="https://bitcoinversus.tech/2026/10/08/osntc-019-spanning-tree-protocol-stp-loops-root-bridge-bpdus-port-roles-rstp/">OSNTC.019: Spanning Tree Protocol</a>.</li><li><strong>Endpoint cannot communicate:</strong> verify whether the endpoint-facing port should be access or trunk mode and confirm its VLAN assignment.</li><li><strong>Intermittent or partial behavior:</strong> compare both ends, review logs and counters, and verify that an EtherChannel is configured consistently.</li></ul><!-- /wp:list -->
<!-- wp:heading --><h2 class="wp-block-heading">PRACTICAL LAB</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Use two lab switches or a network simulator. Create VLANs 10 and 20 on both switches. Place one endpoint-facing port on each switch into VLAN 10 and another into VLAN 20. Configure the inter-switch link as an 802.1Q trunk. Verify that same-VLAN endpoints can communicate across the trunk while VLAN 10 and VLAN 20 remain separate Layer 2 broadcast domains.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Next, restrict the trunk so only VLAN 10 is allowed. Observe that VLAN 10 continues to operate while VLAN 20 loses the inter-switch path. Restore VLAN 20, verify connectivity, then record the trunk's operational mode, native VLAN, and allowed VLAN list. Perform this exercise only in a lab or approved maintenance environment.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">TECHNICIAN WORKFLOW</h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol><li>Identify the two physical interfaces forming the link.</li><li>Confirm link state and interface errors.</li><li>Confirm both interfaces' administrative and operational switchport modes.</li><li>Confirm the required VLANs exist on both switches.</li><li>Confirm the required VLANs are allowed across the trunk.</li><li>Compare native VLAN settings.</li><li>Check spanning-tree state for the affected VLAN.</li><li>Check LACP or port-channel state if the trunk is aggregated.</li><li>Make the smallest approved correction.</li><li>Re-run verification commands and document the before-and-after state.</li></ol><!-- /wp:list -->
<!-- wp:heading --><h2 class="wp-block-heading">KNOWLEDGE CHECK</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><strong>1.</strong> What problem does an 802.1Q trunk solve? <strong>2.</strong> What identifies the VLAN membership of a tagged frame? <strong>3.</strong> What is the difference between an access port and a trunk port? <strong>4.</strong> Why should both ends of a trunk use the same native VLAN? <strong>5.</strong> What happens when VLAN 20 is removed from a trunk's allowed list? <strong>6.</strong> Which command commonly displays active trunks and their allowed VLANs?</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">ANSWER GUIDE</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><strong>1.</strong> It allows multiple VLANs to share one physical Ethernet link. <strong>2.</strong> The 802.1Q tag contains the VLAN identifier. <strong>3.</strong> An access port normally carries one endpoint VLAN, while a trunk carries multiple VLANs. <strong>4.</strong> A mismatch can cause incorrect handling of untagged traffic and network instability. <strong>5.</strong> VLAN 20 can no longer cross that trunk even though the physical link may remain up. <strong>6.</strong> On Cisco IOS-style switches, <code>show interfaces trunk</code>.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2 class="wp-block-heading">CONCLUSION</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>VLAN trunking is the mechanism that lets many logical Layer 2 networks share one physical interconnection. The technician's core responsibilities are to understand what should be tagged, know which VLANs should cross the link, keep native VLAN settings consistent, verify both ends, and avoid changing production switching behavior without evidence. Once trunking is understood, VLAN troubleshooting becomes a structured comparison of interface mode, VLAN existence, allowed lists, native VLANs, spanning-tree state, and the physical path.</p><!-- /wp:paragraph -->
