Windows network troubleshooting is the process of proving, one layer at a time, where communication stops. A technician should be able to distinguish a bad network interface card (NIC) from an incorrect IP configuration, a failed DHCP lease, an unreachable default gateway, broken DNS, a blocked port, or a remote service problem.

This lesson follows OSITC.007: Windows File Sharing and Network Permissions. File sharing depends on working addressing, name resolution, routing, transport protocols, ports, and service availability. OSITC.008 builds the diagnostic workflow needed to prove those dependencies before changing permissions or reinstalling software.

Elementary Overview

Do not begin by resetting the entire network stack. First identify what still works. A PC that can reach its gateway but cannot resolve a hostname has a different fault from a PC with no valid address at all. A system that can resolve a server name but cannot open TCP port 443 has a different fault from one that cannot route to the server.

The fastest troubleshooting process moves from local to remote and from simple to specific: verify the physical interface, inspect the IP configuration, test the local TCP/IP stack, test the gateway, test an external IP address, test name resolution, test the route, then test the actual application port or service.

Learning Objectives

  • Read Windows IPv4 and IPv6 configuration with ipconfig.
  • Recognize valid DHCP addressing, static addressing, APIPA, subnet masks, gateways, and DNS servers.
  • Use ICMP and ping without treating a failed ping as proof that a host is down.
  • Use tracert and routing information to identify path problems.
  • Use nslookup to isolate DNS failures.
  • Use netstat and PowerShell port tests to inspect connections and listeners.
  • Separate Layer 1, Layer 2, Layer 3, DNS, transport, firewall, and application faults.
  • Capture evidence before performing resets or destructive changes.

Start With the Physical Interface

Before interpreting commands, confirm that the NIC is enabled and connected. For wired Ethernet, check the patch cable, switch port, link LEDs, and negotiated speed. Ethernet link negotiation can fail or fall back to an unexpected speed even when Windows reports that an adapter exists.

For Wi-Fi, verify association to the intended SSID and confirm that the device is not connected to a local wireless network with no upstream Internet access. The distinction matters because Wi-Fi can work without Internet connectivity.

Read the Configuration Before Changing It

Run ipconfig /all and record the adapter name, physical address, DHCP state, IPv4 address, subnet mask, IPv6 addresses, default gateway, DHCP server, DNS servers, and DNS suffix. Microsoft’s DNS client troubleshooting guidance begins by checking these values because a name-resolution symptom can actually originate from a bad IP configuration.

A normal dynamically configured client should receive an address that belongs to the intended subnet. An address in the 169.254.0.0/16 range usually indicates Automatic Private IP Addressing (APIPA), meaning Windows did not receive a usable DHCP lease. Do not immediately blame DNS when the client never received a valid gateway or DNS server.

If a DHCP lease is suspect, compare the client with a known-good machine on the same network. Use ipconfig /release and ipconfig /renew only after you have captured the original configuration. A failed renewal can provide useful evidence about the DHCP path that would be lost if the technician resets several subsystems at once.

Know the Addresses You Are Testing

The loopback address 127.0.0.1 represents the local IPv4 host stack. Your assigned interface address represents the local NIC configuration. The default gateway is the router that forwards traffic toward other networks. A public IP address tests reachability beyond the local network. A hostname adds DNS to the test.

This gives the technician a useful progression: local stack → local interface → local gateway → remote IP → remote hostname → application port.

Ping Tests Reachability, Not the Whole Application

Microsoft documents ping as an IP-level connectivity tool based on ICMP echo requests and replies. A successful ping proves that a particular ICMP exchange worked. It does not prove that DNS, HTTPS, SMB, RDP, or another application protocol is healthy.

A failed ping also does not prove that the target is offline. Firewalls and security devices frequently block or rate-limit ICMP while still allowing application traffic. Treat ping as one measurement, not a universal verdict.

  • ping 127.0.0.1 checks the local IPv4 stack.
  • ping <local-IP> checks the configured local address.
  • ping <gateway-IP> tests reachability to the first router.
  • ping <remote-IP> tests IP reachability without requiring DNS.
  • ping <hostname> adds hostname resolution to the test.

Separate DNS From Raw IP Connectivity

One of the most useful comparisons is an IP test versus a hostname test. If a client can reach a known remote IP address but cannot reach a hostname, investigate DNS troubleshooting rather than rebuilding the NIC.

Microsoft’s nslookup queries DNS infrastructure directly. Run nslookup hostname to see which DNS server answers and which records are returned. You can also query a specific resolver by adding its IP address after the hostname.

Use ipconfig /displaydns to inspect the Windows DNS resolver cache. If a stale or negative cached result is confirmed, ipconfig /flushdns clears that cache. Do not use flushdns as a reflex when the real problem is a missing DNS record, unreachable DNS server, incorrect suffix, or blocked DNS traffic.

Trace the Path With tracert

tracert sends packets with progressively increasing IP Time To Live (TTL) values so intermediate routers can reveal the path toward a destination. It is useful when the local gateway is reachable but the remote network is not.

An asterisk in a trace does not automatically mean the path is broken. Some routers do not return the ICMP messages that tracert expects. A later hop may still respond. Look for the point where the behavior changes and compare with a known-good source before declaring a router failed.

Use tracert /d <target> when you want to avoid reverse-DNS lookups and return the route faster. Use pathping when you need longer sampling of latency and packet loss across intermediate hops.

Check the Routing Table

Windows must have a route for the destination. Use route print or netstat -r to inspect the routing table. The default route is normally represented as 0.0.0.0/0 for IPv4 and points toward the system’s preferred gateway.

A system with multiple NICs, VPN adapters, virtual switches, or manually added routes may send traffic through the wrong interface. This is especially important on systems that use VPNs, virtual machines, or several physical network adapters.

Use netstat to See Connections and Listeners

Microsoft’s netstat can display active TCP connections, listening ports, routing information, and protocol statistics. netstat -ano is especially useful because it shows addresses, connection state, and process IDs.

A service can fail locally even when the network is healthy. If an application is supposed to listen on TCP port 443 but no local process is listening, the problem may be the service itself rather than the route or firewall. This is where network troubleshooting connects back to Windows services and process troubleshooting.

Test the Actual TCP Port

ICMP reachability is not the same as application reachability. In PowerShell, Test-NetConnection server.example.com -Port 443 tests whether a TCP connection can be established to the specified host and port. Use the port that matches the actual service: HTTPS, RDP, SMB, SSH, database traffic, or another application.

If ping works but the TCP-port test fails, investigate the Windows Firewall, upstream firewall rules, service state, listening address, TCP/UDP transport, NAT policy, or the destination application. If the port test succeeds but the application still fails, move higher in the stack toward authentication, TLS, application configuration, or permissions.

ARP Helps With Local-Segment Problems

On an Ethernet LAN, Windows uses Address Resolution Protocol (ARP) to map an IPv4 address to a local MAC address. Use arp -a to view cached mappings. A missing or incorrect ARP entry can support investigation of duplicate IP addresses, VLAN problems, unreachable local hosts, or unexpected Layer 2 behavior.

Do not clear the ARP cache before recording it when duplicate addressing or spoofing is suspected. The existing table may contain the evidence that identifies the wrong device.

Do Not Confuse NAT With Local Addressing

A Windows endpoint usually holds a private address while a router or firewall performs NAT or PAT at the network edge. A failure reaching the Internet can therefore originate after the Windows host, even when its local address and gateway are correct.

If many clients fail at the same time, look for a shared fault domain: switch, VLAN, gateway, firewall, WAN circuit, DNS resolver, DHCP server, or upstream provider. If only one machine fails, focus more heavily on its adapter, configuration, routes, firewall, local services, or software stack.

A Repeatable Windows Network Workflow

  1. Record the user symptom, destination, application, exact time, and whether other users are affected.
  2. Verify the NIC is enabled and physically linked or associated to Wi-Fi.
  3. Run ipconfig /all and save the addressing, gateway, DHCP, DNS, and suffix information.
  4. Check for APIPA, wrong subnet, wrong gateway, duplicate address symptoms, or missing DNS servers.
  5. Test the local stack and local interface.
  6. Test the default gateway by IP address.
  7. Test a known remote IP address without DNS.
  8. Test a hostname and compare the result with the raw-IP test.
  9. Use nslookup to query the configured DNS path directly.
  10. Use tracert and route print if the destination is on another network.
  11. Use netstat -ano to inspect active connections or expected local listeners.
  12. Use Test-NetConnection against the application’s real TCP port.
  13. Check local and upstream firewall policy only after identifying which protocol and port are failing.
  14. Correlate with Windows Event Viewer, service state, and application logs.
  15. Change one variable at a time and record the result.
  16. After repair, repeat the original failing test and update the ticket with the confirmed root cause.

Symptom-to-Layer Examples

  • No link light and adapter disconnected: cable, switch port, NIC, or physical interface.
  • 169.254.x.x address: DHCP path, DHCP server, VLAN, or local interface configuration.
  • Can reach gateway but not remote IP: routing, firewall, NAT, WAN, or upstream path.
  • Can reach remote IP but not hostname: DNS server, DNS record, suffix, cache, or resolver path.
  • Hostname resolves but application port fails: firewall, transport path, listener, service, or application state.
  • Port connects but login or share access fails: authentication, permissions, certificates, or application logic.
  • Only one application fails while others work: application-specific proxy, firewall, TLS, service, or configuration problem.
  • Many devices fail simultaneously: shared switch, gateway, DNS, DHCP, firewall, ISP, or infrastructure failure.

Commands Should Produce Evidence

A technician should never run commands only because they appear on a checklist. Each command should answer a question. ipconfig /all asks, “What configuration did Windows receive?” ping asks, “Can this ICMP exchange complete?” nslookup asks, “Can this DNS query be answered?” tracert asks, “What path is visible toward the destination?” netstat asks, “What connections or listeners exist?” Test-NetConnection asks, “Can this TCP port be reached?”

This evidence-first approach prevents random resets from hiding the original fault and makes escalation to a network engineer, server administrator, security team, ISP, or application owner much more useful.

Hands-On Lab

On a Windows training system, capture ipconfig /all, identify the active adapter, note the assigned IPv4 address, subnet mask, gateway, DNS servers, and DHCP state, then test the local gateway. Next test a known remote IP address and a hostname. Use nslookup on the same hostname, run tracert to the destination, inspect route print, and review netstat -ano.

Then use Test-NetConnection against a known service and document the results. With authorization, create one controlled fault such as assigning an incorrect DNS server or disconnecting the test network cable. Predict which tests should fail, perform the sequence, restore the correct configuration, and verify the original working state.

Elementary Conclusion

Windows network troubleshooting becomes easier when every test answers a specific question. Verify the interface, read the configuration, test the gateway, separate IP reachability from DNS, inspect the route, test the actual port, and only then change settings. The goal is not to run every command. The goal is to prove exactly where a working path becomes a failing one.
