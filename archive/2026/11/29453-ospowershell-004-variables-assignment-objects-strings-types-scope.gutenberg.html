Learning Objectives

Understand how PowerShell variables name values, how assignment and expansion work, how objects and types relate to variables, how scope limits changes, and how to inspect variables safely. By the end, the learner should be able to store a command result, examine its type, interpolate a message, distinguish regular variables from environment variables, and explain local versus parent scope.

Prerequisites: A PowerShell 7 installation and an ordinary user account. Review OSPowerShell.001 — Cmdlets, OSPowerShell.002 — Objects, and OSPowerShell.003 — The Pipeline. Every lab command below is designed to avoid changing files, services, or system configuration.

Elementary Overview

A variable is a named place for keeping information while a program works. Imagine attaching a reusable label to a number, a word, or a record about a running application. The label lets a later command use the stored value without typing or retrieving it again. PowerShell labels begin with a dollar sign, such as $count or $process.

PowerShell can hold objects, not only text. A process object, for example, can carry a name and numeric process identifier. The variable refers to the whole object, so the script can read one property when it needs it. Unlike saving a document, ordinary session variables are not automatically preserved after PowerShell exits.

Create, Read, and Update Variables

An assignment uses = to associate a name with a value. Variable names normally begin with a letter or underscore after the dollar sign and should describe what the value represents. PowerShell variable names are case-insensitive by default; $count and $COUNT refer to the same ordinary variable. The following example uses a plain string and an integer.

$computerName = 'lab-workstation'
$retryCount = 3
$computerName
$retryCount
$retryCount = $retryCount + 1
$retryCount

The displayed outputs are lab-workstation, 3, then 4. The final assignment reads the existing numeric value, adds one, and stores the result. Use clear names and avoid accidentally overwriting the automatic variables that PowerShell creates.

A variable can also hold the result of a command. Because the object remains structured, its properties can be accessed later. The special automatic variable $PID identifies the current PowerShell process, making a safe local example.

$currentProcess = Get-Process -Id $PID
$currentProcess.GetType().Name
$currentProcess.ProcessName
$currentProcess.Id

The type name and process name can vary with the operating system and PowerShell host, while the ID is an integer assigned by the operating system. Notice the difference from parsing displayed table text: $currentProcess.Id selects a property of the saved process object. The same object-oriented practice supports Windows process troubleshooting.

Inspect Values and Data Types

PowerShell is dynamically typed: a regular variable may refer to values of different runtime types over time. The value 3 commonly has type System.Int32; the text '3' has type System.String. Use .GetType().FullName or Get-Member to inspect a non-null value instead of assuming the type from its display.

$quantity = 3
$quantity.GetType().FullName       # System.Int32
$quantity = 'three'
$quantity.GetType().FullName       # System.String
[int]$threshold = 5
$threshold.GetType().Name          # Int32

A type-constrained variable such as [int]$threshold requires values convertible to an integer; assigning text such as 'five' produces a conversion error. Basic variable study should stay focused on creating and inspecting values; later lessons introduce arrays and hash tables in greater detail.

Use Get-Variable -Name quantity to inspect metadata and the stored value, or Get-Variable -Name quantity -ValueOnly to retrieve only the value. A separate existence test, Test-Path Variable:quantity, returns a Boolean without depending on the value being non-null.

Get-Variable -Name quantity
Get-Variable -Name quantity -ValueOnly
Test-Path Variable:quantity
Test-Path Variable:noSuchTrainingVariable

Single Quotes, Double Quotes, and Subexpressions

A single-quoted PowerShell string is ordinarily literal: 'Hello $computerName' displays the dollar sign and name. A double-quoted string expands simple variables, so "Hello $computerName" includes the stored text. Use $() for expressions and object properties inside expandable strings. Literal dollar signs in a double-quoted string can also be escaped with a backtick.

$userName = 'Avery'
'Hello $userName'               # Hello $userName
"Hello $userName"               # Hello Avery
"Process ID: $($currentProcess.Id)"
"User: ${userName}_admin"      # User: Avery_admin

The braced variable syntax ${userName} makes the name boundary explicit when adjacent characters might otherwise be read as part of a name. Quotation marks also matter when writing paths or messages. For robust cross-platform path joining, prefer a suitable path cmdlet instead of assuming one operating system’s directory separator.

Scope and Variable Lifetime

Scope determines where a variable name is accessible and where assignments take effect. An interactive session has a global scope; functions and scripts commonly run with their own scopes. Child scopes can read accessible values in parent scopes, but an ordinary assignment in a function normally creates or updates a local value rather than replacing the parent value. Microsoft documents scope explicitly, including Local:, Script:, and Global: modifiers.

$label = 'outside'
function Show-Label {
    $label = 'inside'
    "Function: $label"
}
Show-Label
"Caller: $label"

Expected output is Function: inside followed by Caller: outside. Do not use $Global: merely to avoid passing parameters; global state can make scripts difficult to reuse and test. More advanced automation may require deliberate scope control when working with functions, scheduled tasks, or remoting.

Automatic Variables and Environment Variables

PowerShell supplies automatic variables including $PSVersionTable, $PID, $null, and the current pipeline-item alias $_. Inspect them rather than reassigning them. The environment-variable provider is different: $Env:PATH refers to the process environment, not a normal $PATH session variable. Environment settings can affect launched programs and may contain sensitive information.

$PSVersionTable.PSVersion
$PID
($Env:PATH).GetType().Name
Get-Variable -Name PID

Variables are not a secure secret vault. Avoid printing tokens and passwords, writing secrets to shell history, or assuming a sensitive value is protected merely because it resides in a variable. When administrating computers, apply the account and privilege controls covered in Windows users, groups, and permissions.

Practical Lab — A Read-Only Process Snapshot

Build a small inventory without opening, stopping, or modifying any process. First save the current shell process. Then create a structured summary. The last command interpolates its name and identifier into a readable message. Everything remains in memory within the current session.

$myProcess = Get-Process -Id $PID
$summary = [pscustomobject]@{
    Name = $myProcess.ProcessName
    Id   = $myProcess.Id
}
$summary | Format-List
"Observed $($summary.Name) with PID $($summary.Id)"

Verify the summary is an object by running $summary | Get-Member. Inspect its fields individually with $summary.Name and $summary.Id. The exercise connects variables to prior pipeline lessons while staying within the variable concept. For a different shell-language comparison, the Bash loops and safe iteration lesson offers related operational practice, although Bash expansion and scoping rules are not identical to PowerShell.

Troubleshooting and Common Errors

  • Unexpected blank output: Check spelling and Test-Path Variable:name. An uninitialized variable normally evaluates to $null; strict mode changes some error behavior.
  • Wrong numeric behavior: Check the value’s type. A string such as '10' is not the same as integer 10 in every operation.
  • Unexpected literal dollar sign: Check whether the text was surrounded by single quotation marks.
  • Missing property in a message: Use $($object.Property) inside double quotes, not a bare dotted expression.
  • Value changed only inside a function: Inspect local and parent scope rather than assuming assignments modify the caller.

Practice and Knowledge Check

  1. Create $deviceName and $deviceCount variables, then inspect each value and runtime type.
  2. Compare the output of a single-quoted and a double-quoted string containing $deviceName.
  3. Store the current process in a variable and show only its process name and ID.
  4. Create a function that assigns a local variable with the same name as one in the caller and explain both outputs.
  5. Explain the difference between $Env:PATH and $PATH, and why secrets should not be printed into logs.

Knowledge-Check Answers

  1. A string can contain a device name, while an integer can represent a count; .GetType() identifies each value’s runtime type.
  2. Double quotes expand an ordinary variable, while single quotes ordinarily preserve literal text.
  3. $item = Get-Process -Id $PID, followed by $item.ProcessName and $item.Id, reads the local process without changing it.
  4. The function assignment normally updates its local scope; the caller retains the original value.
  5. $Env:PATH accesses the process environment, whereas $PATH is an ordinary PowerShell variable if defined. Secret values can leak through display, logs, or history.

Elementary Conclusion

A PowerShell variable is a name for information the shell is using. That information might be a number, a word, or a complete record about a program. Assign a value once, retrieve it by name, and inspect its properties whenever a command needs them. Quotes affect how text is built, types affect which operations are possible, and scopes prevent one part of a script from accidentally changing another part’s local work.

Once variables are clear, arrays and hash tables become easier to understand: they let a single name hold a collection of values or named fields. The main habit remains the same—know what is stored, inspect it before using it, and avoid changing system state while learning.
