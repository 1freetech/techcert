An HTML data table describes relationships between values arranged in rows and columns. The correct markup does more than draw a grid: it identifies header cells, names the data, and supplies row–column relationships that assistive technologies can interpret. OSHTML.005 teaches semantic table structure, accessible headers, grouped rows, responsive layout, and practical validation using a small equipment-power example.

The lesson advances the published OSHTML.004: Forms. Earlier lessons covered document structure, element nesting, and attributes. The goal is readable, standards-based markup—not a decorative grid or layout table.

Objectives and prerequisites

  • Recognize when tabular information belongs in <table> instead of a list, paragraph, or CSS layout container.
  • Build rows using <tr>, data cells using <td>, and headers using <th>.
  • Label an entire table with <caption> and group rows with <thead>, <tbody>, and <tfoot>.
  • Assign scope="col" and scope="row" to distinguish column and row headers.
  • Explain when complex header relationships require id and headers or grouping attributes.
  • Create a readable mobile presentation without destroying table semantics.
  • Run a complete HTML sample and 18 structural checks with Node.js.

Prerequisites: an editor, browser, and the HTML fundamentals in OSHTML.001–004. Node.js is needed only for the optional structural test harness. No external packages, credentials, paid services, or administrative privileges are required. The teaching example uses fabricated equipment values and is not a live site measurement.

When to use a table

A table is appropriate when values become meaningful through their intersection with row and column headings. A device-power report may describe a router, switch, and server, along with power and operational state. A list would be more appropriate for a few standalone troubleshooting instructions. Layout tables built to position a page header, sidebar, and footer are discouraged because their cell semantics can confuse assistive technologies and often perform poorly on narrow screens.

The MDN HTML table basics tutorial treats tables as a representation of tabular data, not page layout. The W3C Web Accessibility Initiative tables tutorial emphasizes programmatically determinable header–cell relationships.

Rows, header cells, and data cells

The outer <table> element contains the grid. Each <tr> defines a row. The cells in that row are <th> when they name a row or column, or <td> when they contain regular data. Using <th> only to make text bold is incorrect; use CSS when visual emphasis is required without a heading relationship.

<table>
  <tr>
    <th scope="col">Device</th>
    <th scope="col">Power (W)</th>
  </tr>
  <tr>
    <th scope="row">Router</th>
    <td>12</td>
  </tr>
</table>

scope="col" states that a header applies to cells in its column. scope="row" states that a header applies to cells in its row. For the router’s value, the useful context is both “Router” and “Power (W).” A screen reader can use semantic headers to provide the same context that a visual reader infers from a grid. Simple tables may be understandable without scope, but explicitly setting it makes the relationship clear.

Caption, thead, tbody, and tfoot

A <caption> is a visible title associated with its table; it must appear as the first child of <table>. A caption such as “Illustrative equipment power readings, watts (W)” explains the dataset and the unit. Use a page heading separately if the document needs a broader title.

<table>
  <caption>Example equipment power (W)</caption>
  <thead>
    <tr>
      <th scope="col">Equipment</th>
      <th scope="col">Power (W)</th>
    </tr>
  </thead>
  <tbody>
    <tr><th scope="row">Router</th><td>12</td></tr>
    <tr><th scope="row">Switch</th><td>24</td></tr>
  </tbody>
  <tfoot>
    <tr><th scope="row">Total</th><td>36</td></tr>
  </tfoot>
</table>

<thead> groups header rows, <tbody> contains the primary data, and <tfoot> contains supplementary rows such as a total. Browsers may insert an implicit <tbody> when a table is written without one. Explicit grouping makes author intent clearer and simplifies later CSS selection. The example total of 36 W comes only from 12 + 24 W in the two-row example.

Responsive tables without inaccessible layouts

A three-column table may fit a phone, while a larger schedule may not. Common approaches include fewer columns, shorter values, and a horizontally scrollable region. A wrapping region with max-width:100% and overflow-x:auto can preserve row–column associations rather than converting every cell into a disconnected visual card.

<div class="table-scroll"
     role="region"
     aria-label="Equipment power table"
     tabindex="0">
  <table>...</table>
</div>

<style>
.table-scroll {
  max-width: 100%;
  overflow-x: auto;
}
.table-scroll:focus-visible {
  outline: 2px solid #2563eb;
}
</style>

A focusable scroll region can assist keyboard access to wide content, but unnecessary tab stops should be avoided for tables that never overflow. Always test at narrow widths, higher zoom, keyboard navigation, and screen-reader navigation. The W3C responsive table tips recommend retaining structural relationships through alternate presentations. CSS styling belongs in a stylesheet in larger projects; the sample intentionally keeps a short self-contained lesson.

Spanning cells and complex headers

colspan lets a cell extend across multiple columns, while rowspan extends a cell down multiple rows. Both affect the implied grid. A row with one header spanning two columns does not contain an extra, independent third column unless another cell is provided. Incorrect spans can associate data with the wrong headers, making the table hard to interpret.

<table>
  <caption>Two-zone equipment sample</caption>
  <thead>
    <tr>
      <th scope="col">Zone</th>
      <th scope="col">Device</th>
      <th scope="col">Power (W)</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="rowgroup" rowspan="2">A</th>
      <th scope="row">Router</th><td>12</td>
    </tr>
    <tr><th scope="row">Switch</th><td>24</td></tr>
  </tbody>
</table>

The two-zone example shows rowspan="2" and a row-group header. Its grid structure should be tested with assistive technology; grouping boundaries and spans can be harder to interpret than ordinary one-header rows. More complex matrices may need explicit header identifiers such as <th id="power"> together with <td headers="device-a power"> so an assistive technology can identify the correct labels. Avoid complexity when multiple small tables would be clearer. See W3C’s table-header patterns and MDN table accessibility.

Debugging and safe publication

  • Header association missing: ensure column headers use <th scope="col"> and row labels use <th scope="row">.
  • No table title: include a meaningful <caption> rather than substituting only a heading outside the table.
  • Wrong values under a heading: inspect rowspan, colspan, row group boundaries, and actual cell counts.
  • Mobile overflow: remove avoidable columns, shorten labels, or wrap the grid in a tested scrolling region.
  • Misleading measurements: include units, sample dates, source attribution, and calculated versus observed labels whenever real telemetry is published.
  • Injection and unsafe markup: escape untrusted text before placing it into an HTML table; never concatenate user-controlled data into HTML without context-appropriate encoding.
  • Accessibility assumed from color: do not rely on green/red cell shading alone to communicate equipment status; provide status text.

A table’s structure describes relationships, not the accuracy of the underlying data. Real energy and operations reports must distinguish instantaneous power from accumulated energy, explain sampling periods, and use verified telemetry. In a production project, validate the source values separately from verifying their HTML presentation.

Exercises and knowledge check

  • Build a two-row table with an appropriate caption and two scoped column headers.
  • Convert one device name from <td> to a row-scoped <th>. Explain which relationship changed.
  • Add a fourth illustrative device with power 40 W and update the example total from 186 W to 226 W.
  • Create separate <thead>, <tbody>, and <tfoot> sections, then inspect the browser’s document tree.
  • Try a narrow viewport, keyboard navigation, and 200% zoom. Record any horizontal scrolling and whether each heading remains understandable.
  • Describe the difference between rowspan and colspan, and one case where headers may help.
  • Run the 18 tests, then intentionally remove one scope attribute in a throwaway copy. Explain the failing assertion.

Answer key: a caption names the dataset; a row-scoped th identifies related cells across the row; 186 + 40 = 226 W for the expanded fictional example; header/body/footer grouping clarifies section roles; rowspan covers rows whereas colspan covers columns; explicit headers associations can clarify complex tables; and removing a required scope violates the sample’s tested structural contract. A passing script does not replace manual accessibility review.
