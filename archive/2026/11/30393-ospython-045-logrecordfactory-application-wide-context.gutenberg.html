A Python service can emit diagnostic events from many modules, libraries and worker functions. Adding an identifier to each individual logging call becomes difficult to maintain. The logging.setLogRecordFactory() hook supplies a controlled way to add a consistent field to each newly created LogRecord, while contextvars.ContextVar provides a value associated with the current execution context. Together, they can help operators correlate application events from servers, monitoring collectors and network automation systems.

How Python Creates a Log Record

When an enabled logger handles an event, Python constructs a LogRecord carrying properties such as logger name, level, message template, positional arguments, path, source line and timestamp. Handler filters may then examine a record; handlers send accepted events to destinations, and formatters convert the data to text. The record factory sits earlier: it participates whenever a logger creates a normal record. The official logging library reference documents replacing and retrieving the current factory.

A factory is a callable accepting the usual LogRecord constructor parameters and returning a record. Wrapping the previous factory is safer than discarding it because another framework or instrumentation library may have installed customization already. The wrapper must return a valid record with all standard attributes intact.

A Context Variable Is Not a Global Request Identifier

A normal mutable module-level string is shared by concurrent callers in one process. If two tasks overwrite a single global request ID, their diagnostic lines can be mislabeled. Python's ContextVar instead associates a value with an execution context. Separate asynchronous tasks normally maintain their own context; new threads or separate processes require deliberate handling when continuity is needed. The Python contextvars reference explains context-local values, tokens, and context propagation.

The demonstration uses a single synchronous function, but the same mechanism can be integrated with an asynchronous request handler that sets the ID at request entry and resets the token in a finally clause. Do not assume ContextVar automatically carries a value to a remote API, container, or process; explicit transmission and privacy rules remain necessary.

A Complete Runnable Lab: One Factory, Three Events

Save the following complete source as record_factory_lab.py in a new, unprivileged working directory. It imports only Python standard-library modules. The StringIO destination makes the example deterministic, so it creates no log files and sends no data over the network. The logger's handler and global factory are restored when the function finishes:

"""OSPython.045: application-wide log context, Python 3.12+ stdlib.""" from contextvars import ContextVar import io import logging request_id = ContextVar("request_id", default="unassigned") old_factory = logging.getLogRecordFactory() def context_record_factory(*args, **kwargs): record = old_factory(*args, **kwargs) record.request_id = request_id.get() return record def demo() -> str: output = io.StringIO() handler = logging.StreamHandler(output) handler.setFormatter(logging.Formatter( "%(levelname)s %(name)s id=%(request_id)s %(message)s" )) logger = logging.getLogger("open_cert.telemetry") old_level = logger.level old_propagate = logger.propagate logging.setLogRecordFactory(context_record_factory) logger.setLevel(logging.INFO) logger.propagate = False logger.addHandler(handler) try: logger.info("collector started") token = request_id.set("rack-A7") try: logger.warning("temperature sensor unavailable") finally: request_id.reset(token) logger.info("collector finished") finally: logger.removeHandler(handler) handler.close() logger.setLevel(old_level) logger.propagate = old_propagate logging.setLogRecordFactory(old_factory) return output.getvalue() if __name__ == "__main__": print(demo(), end="")

The original factory is captured before the wrapper is installed. The wrapper delegates ordinary record creation to that factory and adds request_id from the active context. The formatter expects the new field on every record it processes. A try/finally sequence restores the context token after the simulated warning, and another finally removes the handler and restores prior logger state. Restoring global changes is particularly important in unit tests, interactive notebooks, and applications that share a logging process with other libraries.

Run the file from the directory containing the source using the Python interpreter matching your environment:

python --version python record_factory_lab.py

Factory, Filter, and LoggerAdapter: Different Responsibilities

A LoggerAdapter supplies contextual fields to calls made through that adapter. A filter can accept, reject, or modify records at a selected logger or handler. A LogRecordFactory changes record creation across the process for qualifying events. Each solution has a different scope. The earlier logging filters lesson covered selection rules; a factory is useful when a field should exist before downstream formatters examine a newly created record.

Python 3.12 introduced the ability for a handler filter to return a replacement LogRecord instead of simply mutating an existing one. That mechanism can isolate changes to one output handler. A factory remains process-wide, so it should be adopted only when the wider scope is intentional. Refer to the official logging.Filter reference for the version-specific distinction.

Naming Collisions and Secret-Handling Rules

A factory-inserted field must avoid the names Python already reserves for records, including message, levelname, and asctime. The demonstration uses the new attribute request_id. Do not also pass a conflicting extra={"request_id": ...} field on the same event: Logger.makeRecord() rejects an attempt to overwrite an attribute already set on the record, raising a KeyError. Choose one source of truth, or document a different field name for adapter-specific context.

Never add tokens, passwords, private keys, customer secrets, session cookies or entire authorization headers to the factory. A globally injected field reaches more handlers than a developer may expect. Review OSPython.041 on redaction and credential protection before logging identifiers derived from sensitive user data. The public sample uses an invented equipment label and no secrets.

Factories also have performance overhead: every enabled event creates a record and invokes the wrapper. Complex database calls, file reads, blocking network operations or recursive logging inside a record factory can slow down applications or create errors. Keep the wrapper small and predictable. If an application sends logs through a process boundary, serialize appropriate context explicitly rather than assuming that a process-local factory setting has propagated.

Troubleshooting Common Factory Errors

  • KeyError: Attempt to overwrite 'request_id': avoid passing the same field in both a global factory and a per-call extra dictionary.
  • ValueError: Formatting field not found in record: make sure a formatter requiring a custom field is paired with a record producer that actually supplies it.
  • Unexpected duplicate log lines: inspect handler registration and propagate; adding a handler twice or forwarding to the root logger can duplicate output.
  • Incorrect context after work finishes: reset the exact ContextVar token inside a finally clause, including on exception paths.
  • Context absent in a new worker: evaluate how the execution context is propagated into threads, tasks or independent processes.
  • Slow log production: keep the factory lightweight and avoid logging recursively inside the record-creation path.

Knowledge Check and Explained Answers

  1. What does a record factory customize? The creation of eligible LogRecord objects, before downstream handlers format them.
  2. Why call the previous factory? To preserve existing record behavior and avoid replacing framework customizations unnecessarily.
  3. What is the purpose of a ContextVar token? It permits restoring the exact prior context state after a temporary value is assigned.
  4. Does a ContextVar automatically synchronize across separate processes? No. Separate processes require explicit state and correlation handling.
  5. Why does a formatter fail when it references a field missing from the record? Its format string assumes an attribute that the record producer did not set.
  6. Why can a custom request ID conflict with extra? Python prevents per-call extra entries from overwriting an existing record attribute.
  7. What did the executable test validate? The exact event sequence and request IDs, absence of leaked context, and restoration of the original global factory.

Elementary Summary

A record factory gives an application a central place to attach uniform metadata to new Python log events. Used with a context variable, it can expose a temporary synthetic request ID without adding that identifier to every logging statement. Correct implementation delegates to the previous factory, keeps global changes reversible, resets context tokens, avoids record-key collisions and redacts secrets. Testing both the event output and cleanup steps turns a convenient diagnostic technique into a maintainable engineering pattern.
