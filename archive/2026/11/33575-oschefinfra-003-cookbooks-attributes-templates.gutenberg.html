OSChefInfra.003 explores how Chef Infra organizes reusable infrastructure configuration. A cookbook can contain recipes, node attribute defaults, and Embedded Ruby (ERB) templates. Together, those files describe desired settings and produce a configuration suited to a managed machine. The lesson uses fictional service settings and an isolated practice directory, without requiring production access or an operational Chef Infra Server.

The Chef Infra curriculum begins with OSChefInfra.001: Architecture and OSChefInfra.002: Resources and Recipes. Familiarity with OSBash.001: Shell Basics and OSBash.007: Safe Command-Line Arguments helps when working in a Linux sandbox. The current track is OSChefInfra, not the separate Chef esoteric programming language.

Learning objectives

  • Locate metadata.rb, attributes/, recipes/, and templates/ inside a cookbook.
  • Define node defaults and read values through the Chef node object.
  • Pass recipe values into an ERB template using the variables property.
  • Explain how template resources manage the desired contents of a file.
  • Distinguish ordinary Ruby/ERB checks from a real Chef Infra Client convergence run.

What belongs in a cookbook?

A cookbook packages a related set of configuration instructions. A recipe declares resources, metadata.rb identifies the cookbook and version, attributes/default.rb holds default settings, and templates/default/ contains ERB input files. The Chef Infra 19 cookbook guide documents the directory roles. A recipe must be selected by a run list or equivalent local-mode configuration before Chef Infra Client applies its resources.

opencert_lab/
├── metadata.rb
├── attributes/
│   └── default.rb
├── recipes/
│   └── default.rb
└── templates/
    └── default/
        └── settings.conf.erb

Node attributes and precedence

The practice cookbook defines three fictional values: a service label, port 8080, and an enabled flag set to false. Attributes are stored in the Chef node object and may come from cookbooks, policies, or automatic node discovery. Default attributes provide baseline values; higher-precedence settings can replace them according to Chef's documented order. A default is not an immutable constant, and an attribute is not a secure place for plaintext credentials.

# attributes/default.rb
default['opencert_lab']['service'] = 'training-dashboard'
default['opencert_lab']['port'] = 8080
default['opencert_lab']['enabled'] = false

Chef documents the precedence rules in its attribute precedence reference. For a beginner exercise, keep one clearly named default rather than layering normal, override, force-default, and automatic values without understanding their consequences.

Use a template resource to render settings

The recipe declares a directory and a template resource. source 'settings.conf.erb' identifies the ERB file in the cookbook template folder; variables(...) passes service, port, and enabled values. The destination lives only in a temporary exercise directory. Running Chef would create or update files, so the lab belongs in a disposable VM or container, never an unreviewed production host.

# recipes/default.rb
lab_dir = '/tmp/opencert-chef-infra-003'

directory lab_dir do
  mode '0755'
  action :create
end

template "#{lab_dir}/settings.conf" do
  source 'settings.conf.erb'
  mode '0644'
  variables(
    service: node['opencert_lab']['service'],
    port: node['opencert_lab']['port'],
    enabled: node['opencert_lab']['enabled']
  )
  action :create
end

The template reads the values as @service, @port, and @enabled. ERB substitutes each expression into plain text. The expected example output is a fictional service label, port 8080, and enabled=false. The official template resource reference describes source, variables, permissions, and create/update behavior.

# templates/default/settings.conf.erb
# Educational Chef Infra settings. Do not use as a production configuration.
service=<%= @service %>
port=<%= @port %>
enabled=<%= @enabled %>

What was actually tested?

Ruby 3.3.8 compiled the metadata, attribute, recipe, and test files successfully with ruby -c. A standard Ruby ERB renderer produced the expected configuration, and 20 structural and rendering assertions passed. Those checks verify Ruby syntax, the presence of Chef resource declarations, variable references, and the generated text. Chef Infra Client was unavailable in the publication environment, so actual convergence, repeated idempotence, server compatibility, and privilege behavior have not been tested.

In a disposable Linux lab with Chef Workstation properly installed and licensed, administrators can create the cookbook under a configured cookbook path and run a controlled local-mode test. Before a real Chef run, review path ownership, permissions, resources, and any policy restrictions. Chef's Workstation setup guide is the appropriate starting point.

Operational boundaries and knowledge check

  • Where do default attribute declarations go? Commonly attributes/default.rb.
  • Where is the ERB source stored? Under the cookbook's templates/ hierarchy.
  • What passes recipe values to the template? The variables property.
  • Does a successful Ruby syntax test prove Chef converged? No; the Chef client must be exercised separately.
  • Are node attributes suitable for private keys? No; use a dedicated secrets-management mechanism.

Cookbooks keep infrastructure definitions organized. Attributes hold customizable settings, recipes declare desired resources, and ERB templates turn data into configuration files. The boundaries between those layers help teams review changes, repeat deployments, and reduce manual errors. Test carefully before applying changes to real machines.
