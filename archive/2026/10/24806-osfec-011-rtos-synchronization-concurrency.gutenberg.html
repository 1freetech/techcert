Concurrency becomes an engineering problem the moment two execution contexts can touch the same state. In embedded firmware, those contexts may be RTOS tasks, interrupt handlers, DMA completion callbacks, timer callbacks, or work queues. Correct firmware must decide who owns data, how execution contexts communicate, how long blocking is allowed, and what happens when timing assumptions fail.

This lesson follows OSFEC.010: Fault Handling and Post-Mortem Architecture. OSFEC.010 focused on preserving evidence after failure. OSFEC.011 moves earlier in the design cycle and addresses one of the largest sources of difficult embedded failures: shared state, race conditions, deadlocks, priority inversion, missed signals, and incorrect handoff between tasks and interrupts.

Elementary Overview

A scheduler can switch between tasks at almost any legal scheduling point. An interrupt can preempt a task. DMA can modify memory while the CPU is doing something else. On a multicore system, two processors may truly execute at the same time. If two contexts read and write the same object without a defined synchronization rule, the result may depend on timing rather than logic.

Synchronization primitives exist to make timing relationships explicit. A message queue moves data between contexts. A semaphore signals that an event or resource count is available. A mutex gives one thread exclusive ownership of a shared resource. A critical section temporarily prevents unsafe interleaving around a very small operation. These mechanisms are related, but they are not interchangeable.

  • Explain race conditions, atomicity, mutual exclusion, signaling, and message passing.

  • Recognize deadlock, starvation, livelock, queue overflow, and missed-wakeup failure modes.
  • Keep critical sections short enough to preserve real-time behavior.
  • Protect shared hardware such as I²C, SPI, and CAN without creating new timing faults.
  • Instrument concurrency failures with traces, counters, assertions, and debugger evidence.

Race Conditions

A race condition occurs when program correctness depends on the order or timing of concurrent operations. Consider two tasks incrementing the same counter. An increment may require a load from memory, arithmetic in a register, then a store back to memory. If both tasks read the same old value before either writes the new value, one increment can disappear.

The important concept is atomicity. An operation is atomic when other execution contexts cannot observe it halfway completed. Some processor instructions are naturally atomic for aligned machine words; larger data structures and multi-step hardware transactions usually are not. The firmware engineer must know which operations are guaranteed by the processor, compiler, RTOS, and memory model rather than assuming that one line of C executes as one indivisible action.

Prefer Ownership Before Adding Locks

The cleanest synchronization primitive is often architecture. If one task exclusively owns a peripheral or data structure, other tasks do not need to lock it directly. They send commands through a queue and receive results through another queue, notification, or callback. This single-owner pattern reduces the number of places that can corrupt shared state.

For example, instead of allowing five tasks to directly configure the same I²C controller, one bus-manager task can own the controller. Clients submit transaction requests. The bus task serializes them, applies timeouts, handles bus recovery, and returns completion status. The architecture converts uncontrolled shared-hardware access into explicit message passing.

Queues: Move Data Instead of Sharing It

A queue stores messages until a receiving context consumes them. FreeRTOS and Zephyr both provide queue-like kernel objects for inter-task communication. Queues are powerful because the producer and consumer do not need to execute at the same instant, and the message itself establishes a clear handoff boundary.

A queue should have a defined message type, bounded depth, timeout policy, and overflow behavior. If a sensor task can generate 1,000 messages per second while the consumer can process only 500, synchronization is not the real problem; the design has a throughput mismatch. Decide whether to block the producer, drop the newest item, drop the oldest item, aggregate samples, or treat overflow as a fault.

For large buffers, copying every byte through a queue may be inefficient. One common pattern is to place fixed-size buffer descriptors or indexes in the queue while a buffer pool controls ownership of the underlying memory. That pattern becomes especially useful when DMA fills receive buffers asynchronously.

Mutexes: Protect Ownership of a Shared Resource

A mutex is an ownership lock. One task locks it, uses the protected resource, then unlocks it. Other tasks attempting to lock the same mutex either wait, time out, or fail immediately according to the API and timeout policy.

Use a mutex when multiple tasks truly must access one shared resource. Common examples include a shared file system, a bus driver, a logging backend, a configuration structure, or a hardware peripheral that does not support simultaneous transactions. Keep the protected region as small as practical. Acquire the lock, copy or update the necessary state, then release it before performing unrelated computation.

A mutex is normally a task-level primitive. Zephyr explicitly documents that its mutex objects are not designed for interrupt service routines. An ISR cannot safely block waiting for a task that may itself require the ISR or scheduler to make progress.

Semaphores: Signal Events or Count Resources

A semaphore is better understood as a counter with blocking semantics than as ownership. A binary semaphore has a maximum count of one and is commonly used for signaling. A counting semaphore can represent several identical resources or accumulated events.

The distinction matters. A mutex normally has an owner and may implement priority inheritance. A semaphore can be given by one context and taken by another. FreeRTOS documentation specifically distinguishes binary semaphores used for synchronization from mutexes used for mutual exclusion.

A typical ISR-to-task design is: the interrupt handler captures the minimum required hardware status, clears the interrupt source, gives a semaphore or task notification, then exits. A normal task wakes and performs the longer operation. This keeps interrupt latency low and moves blocking work back into schedulable task context.

Interrupt-to-Task Handoff

An interrupt service routine should avoid operations that can sleep, allocate unpredictably, hold a mutex, print large logs, or wait for another context. RTOSes typically provide ISR-safe variants of queue, semaphore, or notification APIs because entering the scheduler from interrupt context requires special handling.

When using DMA, the DMA-complete ISR may place a buffer descriptor into a queue and wake a processing task. The processing task owns that buffer until it explicitly returns it to the free pool. This ownership rule prevents the DMA engine from overwriting memory while software is still consuming it.

Critical Sections

A critical section is a deliberately short region where preemption, interrupts, or competing CPU access is restricted so shared state can be updated consistently. Critical sections are useful for a handful of instructions. They are dangerous when expanded into millisecond-scale work because they increase interrupt latency and damage real-time response.

On an SMP system, disabling interrupts on one CPU does not stop another CPU. A true multiprocessor design may require an atomic primitive or spinlock. Zephyr recommends spinlocks only for brief critical sections and higher-level primitives such as mutexes and semaphores when blocking is acceptable.

Priority Inversion

[youtube https://www.youtube.com/watch?v=C2xKhxROmhA]

DigiKey explains bounded and unbounded priority inversion and demonstrates priority inheritance.

Priority inversion occurs when a high-priority task is blocked by a lower-priority task that owns a required resource. The severe form appears when a medium-priority task repeatedly preempts the low-priority owner. The high-priority task cannot run because it needs the lock; the low-priority task cannot finish because the medium-priority task keeps preempting it.

Many RTOS mutex implementations use priority inheritance: the low-priority mutex owner temporarily inherits the priority of the highest-priority waiter so it can finish the protected work and release the resource. Current FreeRTOS documentation describes mutexes as including priority inheritance, while binary semaphores do not. Zephyr likewise implements priority inheritance for mutexes.

A recent embedded-systems discussion revisits the Mars Pathfinder priority-inversion incident and why priority inheritance became a classic real-time systems lesson. Community discussion is supplementary; RTOS behavior should be confirmed against the actual kernel documentation.

Deadlock

[youtube https://www.youtube.com/watch?v=hRsWi4HIENc]

DigiKey demonstrates deadlock and starvation using the dining-philosophers concurrency problem.

A deadlock occurs when contexts wait forever for one another. The classic firmware case uses two locks. Task A owns Mutex 1 and waits for Mutex 2. Task B owns Mutex 2 and waits for Mutex 1. Neither can continue, so neither can release what the other needs.

A practical prevention rule is to define a global lock order. If every task must acquire Bus Lock before Filesystem Lock, no task may acquire them in the reverse order. Additional defenses include lock timeouts, avoiding nested locks, using one owner task for complex resources, and instrumenting lock-acquisition failures instead of waiting forever.

Starvation and Livelock

Starvation means a task remains ready or repeatedly waits for a resource but rarely receives enough execution time or access to make progress. A poorly designed high-priority polling task can starve background work even without any deadlock.

Livelock is different: tasks continue executing and changing state, but their reactions prevent useful progress. Two state machines that repeatedly back off and retry in perfect synchronization can consume CPU indefinitely without completing the transaction.

Shared Bus Example

Assume a high-priority sensor task and a low-priority temperature task both need one I²C bus. A medium-priority telemetry task does not use the bus. If the low-priority task takes the bus mutex just before the high-priority task becomes ready, the high-priority task blocks. Without priority inheritance, the medium-priority telemetry task may preempt the low-priority task, indirectly delaying the highest-priority work.

The immediate fix may be a mutex with priority inheritance. The stronger architectural fix may be an I²C owner task receiving transactions through a queue. Which design is better depends on required latency, bus traffic, driver API, memory budget, failure recovery, and how many clients share the peripheral.

Concurrency Around SPI and CAN

An SPI controller may serve several chip-select devices that require different clock modes and frequencies. Protect the controller configuration and complete transaction as one logical operation so another task cannot change mode halfway through a transfer.

A CAN driver often has separate transmit queues, receive FIFOs, interrupt callbacks, and application tasks. The concurrency design must define which context owns each buffer and how bus errors, retries, and queue saturation propagate to application logic.

Watchdogs Are Not a Synchronization Strategy

A watchdog timer can recover a system that stops making progress, but it does not make unsafe concurrency correct. If a deadlock resets the device every twenty seconds, the watchdog has exposed the symptom while the firmware still contains the defect.

Design the watchdog so its health decision depends on meaningful task progress rather than one timer callback blindly feeding it. A supervisory task can require periodic heartbeats or progress counters from critical tasks before refreshing the hardware watchdog.

Instrument the Scheduler, Not Just the Application

Concurrency faults are easier to diagnose when the firmware records task state, high-water stack usage, queue depth, maximum queue depth, failed queue sends, mutex timeouts, semaphore wait times, ISR counts, scheduler latency, and watchdog progress. Feed this evidence into the post-mortem architecture rather than relying only on a generic crash code.

Use JTAG, SWD, OpenOCD, and GDB to inspect blocked task stacks, mutex owners, queue state, and scheduler objects when the target can be halted without destroying the failure. Use the serial console or trace transport when halting changes timing too much.

Bootloaders Need Concurrency Discipline Too

A bootloader often runs before the full RTOS, but firmware-update code may execute later under an RTOS while networking, storage, power monitoring, and flash drivers are active. Flash erase/write operations can block buses, disable interrupts, or conflict with execute-in-place behavior. Treat update state, flash ownership, image metadata, and reset sequencing as concurrency-sensitive resources.

Engineering Rules

  1. Prefer one clear owner for complex mutable resources.
  2. Pass messages instead of sharing writable globals when practical.
  3. Use mutexes for ownership and mutual exclusion.
  4. Use semaphores or task notifications primarily for signaling.
  5. Keep interrupt handlers short and never make them wait on task-owned resources.
  6. Keep critical sections extremely short.
  7. Define queue depth and overflow behavior explicitly.
  8. Define lock ordering before multiple locks are introduced.
  9. Use timeouts where an infinite wait would hide a failure.
  10. Measure worst-case lock hold time, not just average time.
  11. Account for priority inversion when tasks of different priorities share resources.
  12. Log synchronization failures into the crash and post-mortem system.
  13. Test timing under load, not only on an idle bench.

Hands-On Engineering Exercise

Build three RTOS tasks on a development board. Task A periodically samples a sensor at high priority. Task B prints status at medium priority. Task C reads a second device on the same I²C bus at low priority. First protect the bus with a plain binary semaphore and deliberately hold the resource long enough to observe scheduling behavior. Record when Task A becomes ready, when it blocks, and how long Task C takes to release the bus.

Then replace the synchronization mechanism with the RTOS mutex implementation and observe whether priority inheritance changes Task C's effective priority. Finally, redesign the system so one I²C manager task owns the bus and Tasks A and C submit transactions through a queue. Compare latency, code complexity, timeout handling, and observability across the three architectures.

Elementary Conclusion

Reliable concurrent firmware depends less on adding locks everywhere and more on making ownership explicit. Use queues to transfer data, semaphores to signal, mutexes to protect shared ownership, critical sections only for tiny atomic operations, and ISR-safe mechanisms for interrupt handoff. Then verify the design under real timing pressure with traces and fault evidence.
