<!-- wp:heading --><h2 class="wp-block-heading">Elementary Overview</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>On <strong>Linux</strong>, a user password can have a schedule as well as a value. The <strong><code>chage</code></strong> command manages that schedule: when a password was last changed, how long it may be used, how early the user is warned, how long an expired password may remain inactive, and when the account itself expires. It works alongside <a href="https://bitcoinversus.tech/2026/10/02/linux-command-37-passwd/"><strong><code>passwd</code></strong></a>, which changes or expires passwords, and the account-management commands <a href="https://bitcoinversus.tech/2026/10/03/linux-command-38-useradd/"><strong><code>useradd</code></strong></a>, <a href="https://bitcoinversus.tech/2026/10/03/linux-command-39-usermod/"><strong><code>usermod</code></strong></a>, and <a href="https://bitcoinversus.tech/2026/10/06/linux-command-43-userdel/"><strong><code>userdel</code></strong></a>. The simplest mental model is that <code>passwd</code> manages the password itself, while <code>chage</code> manages the password’s calendar.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Read the Current Aging Policy With chage -l</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>The safest first step is inspection. <code>sudo chage -l alice</code> lists the account’s current password-aging values in human-readable form: last password change, password expiration date, inactive period, account expiration date, minimum days between changes, maximum days before expiration, and warning days. That makes <code>chage -l</code> a useful companion to <a href="https://bitcoinversus.tech/2026/10/02/linux-command-36-getent/"><strong><code>getent</code></strong></a> when auditing local account state. Reading before writing is especially important on production systems because an aggressive aging change can force an unexpected password reset or make an account unavailable at the next login.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Set Minimum, Maximum, Warning, and Inactive Periods</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>The main policy switches correspond to stages on a password-aging timeline. <code>sudo chage -m 1 alice</code> sets a minimum of one day before another password change is allowed; <code>sudo chage -M 90 alice</code> sets a 90-day maximum age; <code>sudo chage -W 7 alice</code> warns the user seven days before expiration; and <code>sudo chage -I 14 alice</code> allows fourteen inactive days after password expiration before the account becomes unavailable. These values should come from the organization’s real authentication policy rather than arbitrary numbers. The command provides the mechanism; security policy determines the correct settings.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Force a Password Change or Set an Account Expiration Date</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><code>sudo chage -d 0 alice</code> sets the last-password-change value so the user must choose a new password at the next applicable login. This is useful for temporary passwords created during account provisioning, and it overlaps conceptually with the expiration behavior available through <a href="https://bitcoinversus.tech/2026/10/02/linux-command-37-passwd/"><code>passwd</code></a>. A separate control, <code>sudo chage -E 2026-12-31 alice</code>, sets an expiration date for the account itself. Password expiration and account expiration are different: one says the credential is too old, while the other says the account has reached the end of its permitted lifetime.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">chage Works Through /etc/shadow, Not Through a Separate Password Database</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Password-aging metadata for local Linux accounts is stored in <strong><code>/etc/shadow</code></strong>. Fields represent the last password change as a day count, minimum and maximum ages, warning period, inactivity period, and account expiration. <code>chage</code> gives administrators a safer human-readable interface to those values instead of manually editing the protected file. Defaults for newly created local accounts can also be influenced by configuration such as <code>/etc/login.defs</code>, while authentication frameworks such as PAM may enforce additional password-quality or login policy. This separation is why changing one <code>chage</code> value does not automatically define every aspect of Linux authentication security.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Elementary Conclusion</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><code>chage</code> is basically a calendar manager for a Linux user account. The password is still the secret used to prove identity, but <code>chage</code> can say how long that secret is allowed to remain valid, when the user should be warned, how long an expired password may remain inactive, and when the entire account should stop working. A careful administrator first reads the current policy, changes only the required field, and reads it again to verify the result. Together with <a href="https://bitcoinversus.tech/2026/10/03/linux-command-38-useradd/">user creation</a>, <a href="https://bitcoinversus.tech/2026/10/03/linux-command-39-usermod/">account modification</a>, <a href="https://bitcoinversus.tech/2026/10/02/linux-command-37-passwd/">password management</a>, and <a href="https://bitcoinversus.tech/2026/10/06/linux-command-43-userdel/">account removal</a>, it completes an important part of the Linux user-account lifecycle.</p><!-- /wp:paragraph -->
