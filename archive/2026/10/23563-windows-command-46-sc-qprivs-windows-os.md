<!-- wp:paragraph --><p><strong><code>sc.exe qprivs</code> queries the required-privileges configuration for a Windows service.</strong> It is a read-only Service Control Manager command: it shows which Windows privileges a service declares that it needs when its process starts, without changing the service.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>This continues the Service Control Manager sequence after <a href="https://bitcoinversus.tech/2026/10/11/windows-command-45-sc-qfailureflag-windows-os/">Windows Command #45 – sc qfailureflag</a>. The command that changes this setting is <code>sc.exe privs</code>; this lesson focuses only on inspecting the current configuration safely.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2>What required privileges mean</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Windows services run inside a security context. That account may possess many operating-system privileges, but Windows Service Hardening lets a service declare a smaller required set. When that list is configured, the Service Control Manager removes privileges that the service did not request from the process token when the process starts. This reduces the power available to the service if it is compromised.</p><!-- /wp:paragraph -->

A service’s required-privilege list is a separate Service Control Manager configuration that can further reduce its process token. Source: Microsoft Learn.</em></figcaption></figure><!-- /wp:image -->
<!-- wp:heading --><h2>Basic syntax</h2><!-- /wp:heading -->
<!-- wp:code --><pre class="wp-block-code"><code>sc.exe qprivs SERVICE_NAME</code></pre><!-- /wp:code -->
<!-- wp:paragraph --><p>Replace <code>SERVICE_NAME</code> with the service name, not necessarily the friendly display name. For a disposable example service:</p><!-- /wp:paragraph -->
<!-- wp:code --><pre class="wp-block-code"><code>sc.exe qprivs DemoService</code></pre><!-- /wp:code -->
<!-- wp:paragraph --><p>A successful query can return privilege names such as <code>SeImpersonatePrivilege</code>, <code>SeCreateGlobalPrivilege</code>, or <code>SeIncreaseWorkingSetPrivilege</code>. The exact list depends on the service. Do not assume that every service should have the same privileges.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2>An empty list does not mean no privileges</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>This is the most important interpretation rule. Microsoft documents that if no required-privilege list is configured, the Service Control Manager uses the privileges normally available to the service process token. In other words, an empty <code>qprivs</code> result can mean that no privilege-reduction list has been configured—not that the service runs with zero privileges.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>For compatibility, <code>SeChangeNotifyPrivilege</code> is never removed from a service process token by this mechanism, even when it is not explicitly listed.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2>Shared-process services need extra care</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Many Windows services share a host process such as <code>svchost.exe</code>. When multiple services share one process, Windows computes the <strong>union</strong> of the privileges required by every service in that process. One service can therefore cause a privilege to remain available to the shared process even when another service does not request it.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>This is why <code>qprivs</code> should be interpreted alongside the service type and hosting model. Use <code>sc.exe qc SERVICE_NAME</code> and <code>sc.exe queryex SERVICE_NAME</code> when you need more context about configuration and process identity.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2>Query a remote system</h2><!-- /wp:heading -->
<!-- wp:code --><pre class="wp-block-code"><code>sc.exe \\SERVER01 qprivs DemoService</code></pre><!-- /wp:code -->
<!-- wp:paragraph --><p>Remote queries require network connectivity and sufficient Service Control Manager permissions on the target computer. An access-denied response means the query was not authorized; it does not prove that the service has no required-privilege configuration.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2>Why this matters for security</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Privileges are powerful operating-system capabilities. Some allow a process to impersonate another security context, back up protected data, restore files, change system time, or perform other sensitive operations. A service that does not need a capability should not retain it merely because the underlying account has it.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>The goal is least privilege: enough rights for the service to function, but no more. <code>qprivs</code> gives administrators a fast way to audit the configured list before making changes.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p><em>Related social discussion:</em> <a href="https://www.reddit.com/r/sysadmin/comments/11gc1bn/tricky_permissions_checking_on_windows_10/">r/sysadmin discussion on Windows privilege requirements</a>, including SeTcbPrivilege, SeIncreaseQuotaPrivilege, and SeAssignPrimaryTokenPrivilege.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2>Do not change service privileges casually</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><code>qprivs</code> is safe because it only reads configuration. The companion <code>sc.exe privs</code> command changes the required-privilege list and can prevent a service from working if a needed privilege is removed. Microsoft explicitly recommends determining the minimum required set and testing changes thoroughly in an isolated environment.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Required privileges also cannot magically grant a service rights that its configured account does not possess. The mechanism is designed to reduce available privileges, not to elevate the account.</p><!-- /wp:paragraph -->
<!-- wp:heading --><h2>Useful verification commands</h2><!-- /wp:heading -->
<!-- wp:list --><ul><li><code>sc.exe qprivs SERVICE_NAME</code> — read the required-privilege list.</li><li><code>sc.exe qc SERVICE_NAME</code> — inspect the service configuration and account.</li><li><code>sc.exe queryex SERVICE_NAME</code> — inspect status plus process information.</li><li><code>sc.exe qsidtype SERVICE_NAME</code> — inspect the service SID type.</li><li><code>whoami /priv</code> — inspect privileges in the current interactive process token; this is not the same as the service’s configured required-privilege list.</li></ul><!-- /wp:list -->
<!-- wp:heading --><h2>Practice lab</h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol><li>Open an elevated Command Prompt on a lab Windows system.</li><li>Choose a noncritical service and record its service name.</li><li>Run <code>sc.exe qc SERVICE_NAME</code> and note the service account and process type.</li><li>Run <code>sc.exe qprivs SERVICE_NAME</code> and record the output exactly.</li><li>If the list is empty, explain why that does not mean the process has no privileges.</li><li>Run the same query against a second service and compare the results.</li><li>Do not modify the privilege list during this exercise.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2>Key takeaway</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><strong><code>sc.exe qprivs</code> is an audit command for Windows Service Hardening.</strong> It shows the privilege-reduction list a service has declared, but the output must be interpreted carefully—especially when the list is empty or the service shares a process with other services.</p><!-- /wp:paragraph -->
