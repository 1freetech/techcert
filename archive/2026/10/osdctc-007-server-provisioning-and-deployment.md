<!-- wp:heading --><h2 class="wp-block-heading">Elementary Overview</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><strong>Server provisioning</strong> is the process of taking a physical server from installed hardware to a verified machine that is ready for production use. A technician may begin with a server that has just been mounted in a rack and end with a system whose firmware, storage, operating system, network settings, monitoring, asset records, and handoff documentation have all been checked.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>This lesson follows <a href="https://bitcoinversus.tech/2026/10/08/osdctc-006-bmc-out-of-band-server-management-ipmi-idrac-ilo-redfish-remote-console-recovery/"><strong>OSDCTC.006: BMC and Out-of-Band Server Management</strong></a>. The previous lesson explained how technicians use iDRAC, iLO, remote console, event logs, and out-of-band power control. Provisioning uses those same management tools to prepare a server deliberately before it carries a real workload.</p><!-- /wp:paragraph -->
<!-- wp:image {"id":22798,"sizeSlug":"full","linkDestination":"none"} --><figure class="wp-block-image size-full"><img src="https://bitcoinversus.wordpress.com/wp-content/uploads/2026/10/osdctc007-body.jpg" alt="Data center team installing a rack server and configuring deployment cabling" class="wp-image-22798" /><figcaption class="wp-element-caption"><em>Server provisioning joins physical installation, firmware, storage, networking, operating-system deployment, validation, and documentation into one controlled workflow.</em></figcaption></figure><!-- /wp:image -->

<!-- wp:heading --><h2 class="wp-block-heading">Provisioning Starts With Identity</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Before changing firmware or installing an operating system, confirm that the physical machine matches the work order. Verify the rack and U position, chassis service tag or serial number, asset number, hostname assignment, management address, and intended role. This prevents one of the most damaging deployment mistakes: configuring the correct procedure on the wrong server.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>The identity check connects directly to <a href="https://bitcoinversus.tech/2026/10/06/osdctc-004-server-rack-and-stack-rail-kits-u-positions-airflow-power-network-verification/"><strong>rack-and-stack verification</strong></a>. A server should already have correct rails, airflow orientation, power connections, network cabling, and management connectivity before software provisioning begins.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Record The Baseline Before Changing Anything</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Record the starting state: firmware versions, CPU and memory inventory, drive count, storage-controller state, NIC inventory, BMC address, current boot mode, Secure Boot state, hardware-health status, and any active faults. If a problem appears later, the baseline shows whether it existed before the provisioning work.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Use the BMC hardware inventory and lifecycle logs when available. If the server already reports failed DIMMs, degraded storage, a missing power supply, or thermal alarms, stop and resolve the hardware problem instead of installing software on top of an unhealthy platform. <a href="https://bitcoinversus.tech/2026/10/07/osdctc-005-server-hardware-troubleshooting-post-bmc-logs-dimms-drives-psus-fault-isolation/"><strong>OSDCTC.005</strong></a> covers that fault-isolation workflow.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Check BIOS Or UEFI Configuration</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Modern servers normally use <a href="https://bitcoinversus.tech/2026/04/30/bios-versus-uefi-2/"><strong>UEFI</strong></a> rather than legacy BIOS boot. Review the boot mode, boot order, Secure Boot policy, virtualization settings, CPU power profile, memory configuration, embedded NIC settings, and any facility-specific requirements before installing the operating system.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Do not change settings simply because an option exists. Provisioning should reproduce an approved standard. A large fleet is easier to troubleshoot when equivalent servers use the same firmware settings, storage layout, NIC configuration, and deployment method.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Storage Must Be Ready Before The OS Is Installed</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>The operating system needs a valid installation target. Depending on the server, that may be a single SSD, mirrored boot drives, a RAID virtual disk, NVMe devices, a SAN LUN, or another approved storage design. Confirm drive health and make sure the intended boot device is visible to firmware.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>On systems using a RAID controller, create or verify the required virtual disk before deployment. Dell’s official <a href="https://www.dell.com/support/manuals/en-us/poweredge-r640/idrac9_6.xx_lc_ug/operating-system-deployment?guid=guid-400ae3ad-453a-4747-84b2-5273c1844877"><strong>Lifecycle Controller operating-system deployment documentation</strong></a> explicitly supports configuring RAID before OS installation and supports both manual and unattended installation. The exact RAID level and disk policy should come from the approved server build standard, not technician preference.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Choose The Deployment Method</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Common deployment paths include local USB media, BMC virtual media, vendor lifecycle tools, a network installation system, or a fully automated provisioning platform. Small environments may install one machine manually. Large fleets usually favor repeatable automation because manual configuration becomes slow and inconsistent at scale.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p><a href="https://bitcoinversus.tech/2026/10/07/what-is-pxe-boot-network-operating-system-deployment/"><strong>PXE boot</strong></a> allows a server to start an installation workflow from the network. The UEFI specification describes network boot as using PXE-related mechanisms in which the booting platform interacts with network services such as <a href="https://bitcoinversus.tech/2026/10/01/osntc-005-dhcp-basics/"><strong>DHCP</strong></a> and a system that provides a boot image. The <a href="https://uefi.org/specs/UEFI/2.10/03_Boot_Manager.html?highlight=bootx64+efi"><strong>UEFI Boot Manager specification</strong></a> explains this network-boot path.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">PXE Depends On The Network Working Correctly</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>If a server will not network boot, treat the problem as a layered network fault instead of immediately blaming the installer. Verify physical link, switch port, <a href="https://bitcoinversus.tech/2026/09/30/osntc-004-vlan-basics/"><strong>VLAN</strong></a>, DHCP response, correct boot-interface selection, firmware boot mode, and reachability to the deployment infrastructure.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>A production NIC and a BMC management port are different interfaces. Make sure the cable connected to the host <a href="https://bitcoinversus.tech/2026/10/07/networking-what-is-nic-network-interface-card-servers-asic-miners/"><strong>NIC</strong></a> is on the network that actually provides PXE service. A perfectly reachable iDRAC or iLO session does not prove that the host NIC can reach the provisioning network.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Install The Operating System From An Approved Image</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>The installation image should be the exact approved version for the server role. Confirm the operating-system release, edition, architecture, image checksum when your process requires it, and any required unattended-installation configuration before starting. Avoid random installation media or an untracked technician USB drive.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>During installation, confirm the intended boot disk before accepting destructive storage changes. For unattended builds, verify that the automation selected the expected hostname, disk layout, network configuration, package set, and security baseline.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Firmware And Drivers Must Match The Platform</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>After the operating system is installed, confirm required chipset, storage, network, accelerator, and management drivers. Also verify the approved firmware baseline for the BMC, system BIOS/UEFI, RAID controller, NICs, drives, and other field-upgradable devices.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Avoid updating every component during an unrelated deployment just because a newer version exists. Use the approved compatibility matrix or build standard. Firmware changes can alter boot behavior, device compatibility, power management, security controls, and hardware initialization, so treat them as controlled changes.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Validate Hardware Before Calling The Build Complete</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Check CPU count, memory capacity, storage health, network-interface inventory, power-supply status, fans, temperatures, and event logs after installation. Compare the observed hardware against the work order or bill of materials. A server can boot successfully while still missing a DIMM, operating with a degraded RAID set, or using only one of two intended network paths.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Clear only the alarms that the procedure authorizes you to clear, and only after evidence has been captured. Reboot when required by the build, then confirm the system returns cleanly with no new POST, BMC, storage, or operating-system errors.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Validate The Network Path</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Confirm link speed and duplex, expected VLAN membership, IP addressing, default gateway, DNS resolution, and reachability to required management or service endpoints. If the build uses redundant links or multiple NICs, verify the intended ports rather than assuming every connected cable is active.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>For troubleshooting, work from the physical layer upward: cable and link light, switch port, VLAN, IP configuration, gateway, DNS, then application service. This method prevents technicians from changing operating-system settings when the actual problem is a patch cable, disabled switch port, wrong VLAN, or missing DHCP scope.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Monitoring Is Part Of Provisioning</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>A server that is not visible to monitoring is not fully operational. Confirm that the BMC, host operating system, or both report to the expected monitoring platform. Verify hardware alarms, uptime checks, telemetry, and any required <a href="https://bitcoinversus.tech/2026/10/07/networking-what-is-snmp-bitcoin-mining-switch-pdu-monitoring/"><strong>SNMP</strong></a> or API integration.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Monitoring should be tested before handoff. Do not assume that enrollment succeeded merely because an agent package was installed. Verify that the monitoring system actually sees the new server and that test alarms or health data appear where operators expect them.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Burn-In And Functional Tests Catch Early Failures</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Some environments perform burn-in or workload validation before production handoff. That can include memory tests, CPU stress, storage checks, network throughput checks, repeated reboots, temperature observation, and application-specific tests. The goal is to expose early component failures and configuration mistakes before users depend on the machine.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>Testing should match the approved procedure. A technician should not invent an uncontrolled stress test on production equipment. Record the tool, duration, result, temperatures, hardware errors, and final health status when burn-in evidence is required.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">Document The Build And Handoff</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Update the asset system, ticket, CMDB, rack record, hostname record, serial number, management address, production addresses, firmware baseline, storage layout, operating-system version, monitoring state, and any exceptions. Good documentation turns a one-time deployment into a supportable system.</p><!-- /wp:paragraph -->
<!-- wp:paragraph --><p>The handoff should answer a simple question: can the next technician understand what was built without guessing? If the answer is no, the provisioning task is not complete.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading">A Practical Provisioning Sequence</h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol class="wp-block-list"><li>Confirm work order, rack/U position, asset tag, serial number, and intended server role.</li><li>Verify rails, airflow, A/B power, host networking, and BMC management connectivity.</li><li>Record firmware, hardware inventory, boot mode, storage state, and active alarms.</li><li>Resolve hardware faults before installing software.</li><li>Apply the approved BIOS/UEFI and Secure Boot configuration.</li><li>Configure or verify the intended boot storage and RAID layout.</li><li>Select the approved deployment path: PXE, virtual media, local media, vendor lifecycle tool, or automation platform.</li><li>Install the approved operating-system image.</li><li>Install or verify required drivers and approved firmware.</li><li>Validate CPU, memory, storage, NICs, temperatures, fans, PSUs, and logs.</li><li>Validate network addressing, VLAN, DNS, gateway, and required service reachability.</li><li>Confirm monitoring and management enrollment.</li><li>Run required burn-in or functional tests.</li><li>Reboot and verify a clean return to service.</li><li>Update asset records, ticket evidence, configuration records, and handoff notes.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading">Common Technician Mistakes</h2><!-- /wp:heading -->
<!-- wp:list --><ul class="wp-block-list"><li><strong>Provisioning the wrong chassis:</strong> verify physical and logical identity before changing anything.</li><li><strong>Installing on unhealthy hardware:</strong> resolve BMC, memory, storage, PSU, fan, or thermal faults first.</li><li><strong>Using an unapproved image:</strong> deployment media should be controlled and traceable.</li><li><strong>Installing to the wrong disk:</strong> confirm the intended boot device before destructive storage operations.</li><li><strong>Confusing BMC reachability with host-network reachability:</strong> they are separate paths.</li><li><strong>Skipping monitoring validation:</strong> an installed agent is not proof that operations can see the server.</li><li><strong>Changing extra firmware or settings during deployment:</strong> unnecessary variables make failures harder to isolate.</li><li><strong>Closing the ticket without evidence:</strong> record what was changed, tested, and verified.</li></ul><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading">Exercises</h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol class="wp-block-list"><li>Create a pre-provisioning checklist for a newly racked dual-PSU server.</li><li>Explain why the technician should record the BMC hardware inventory before installing the operating system.</li><li>A server reaches iDRAC but PXE fails. List the next six checks in order.</li><li>Describe when RAID configuration must occur relative to OS installation.</li><li>Explain the difference between a successful OS boot and a completed production handoff.</li><li>Create a post-install validation list covering hardware, network, monitoring, and documentation.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading">Knowledge Check + Answers</h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol class="wp-block-list"><li><strong>What is server provisioning?</strong> The controlled process of preparing physical server hardware, firmware, storage, networking, operating system, monitoring, validation, and records for service.</li><li><strong>Why verify identity first?</strong> To prevent configuring or wiping the wrong physical server.</li><li><strong>Why check hardware health before installing the OS?</strong> Software installation does not repair failed DIMMs, degraded storage, bad PSUs, thermal faults, or other hardware problems.</li><li><strong>What does PXE provide?</strong> A method for starting a server from network-provided boot resources so an operating system or deployment environment can be loaded remotely.</li><li><strong>Why is RAID often configured before the OS?</strong> The installer needs the correct logical boot target before writing the operating system.</li><li><strong>Why validate monitoring before handoff?</strong> Operations teams need confirmed visibility into the new server’s health and availability.</li><li><strong>What makes documentation part of provisioning?</strong> Accurate records make the server maintainable, auditable, and supportable after the installer leaves.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading">Elementary Conclusion</h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Provisioning turns a newly installed server into a known, repeatable, supportable system. The technician verifies identity, records the baseline, checks firmware, prepares storage, deploys the operating system, verifies drivers and firmware, validates hardware and networking, confirms monitoring, tests the machine, and documents the final state. The most important habit is consistency: build from an approved standard, capture evidence, and verify each layer before handoff.</p><!-- /wp:paragraph -->
