Linux Command #69 introduces systemd-cat, a small utility that sends a program's text output to the systemd journal. On a Linux server, application messages can arrive through stdout, stderr or logging APIs, while the journal provides a common place to inspect them. Earlier, Linux Command #28 explained how to read journal entries. The new lesson works in the opposite direction, sending a deliberately harmless test entry and retrieving it by a unique identifier.

What systemd-cat does

The upstream systemd-cat manual documents two modes. With no command argument, the utility reads text from standard input, useful at the end of a shell pipeline. With a command argument, it runs the program and connects both its standard output and standard error to the journal. A pipeline only sends the upstream command's standard output unless the shell explicitly redirects stderr. Choosing the command form can therefore preserve errors otherwise missed by a pipe.

The --identifier option assigns a short tag, while --priority sets the default message severity. Supported values include debug, info, notice, warning and err. A systemd-enabled Linux environment with an accessible journal is needed; a minimal container without a running journal service may not support the exercise.

Send one identifiable test message

On an authorized development machine, run the following command. The message contains no credentials, user data or actual equipment status. The identifier bv-lesson69 makes the new entry easy to locate later.

printf '%s\n' 'lesson69 synthetic test message' | systemd-cat --identifier=bv-lesson69 --priority=notice

The pipeline passes one line of text to systemd-cat. The journal receives the entry with a notice default priority, which corresponds to syslog priority 5. The command does write a record into the local journal; do not run it on production systems without authorization. A successful shell exit code alone does not prove an entry was retained, exported or delivered to a remote monitoring service.

Read back the message

Use journalctl to filter by the assigned identifier and a short time window. The official journalctl reference documents -t for matching SYSLOG_IDENTIFIER and --since for time filtering.

journalctl -t bv-lesson69 --since "10 minutes ago" --no-pager

Look for the text lesson69 synthetic test message. The output also includes local timestamps and source information chosen by the system. A missing match is not automatically evidence that systemd-cat is broken; first confirm the journal service is active, the host clocks are reasonable, and the user has permission to read the entry. An unprivileged account may only see a subset of journal records.

Severity and command mode

The priority can also be supplied by a syslog-style line prefix when --level-prefix is enabled, as it is by default. Prefix <4> means warning. Keep the test identifier distinct from actual production alerts, and compare the stored priority after running:

printf '<4>lesson69 synthetic warning\n' | systemd-cat -t bv-lesson69
journalctl -t bv-lesson69 -p warning --since '10 minutes ago' --no-pager

For a standalone program rather than a pipeline, systemd-cat --identifier=bv-lesson69 /usr/bin/printf '%s\n' 'command-mode check' attaches the invoked program's output to the journal. Unlike the pipeline example, command mode also captures stderr. A custom --stderr-priority can assign different default severities to stdout and stderr, although using separate channels may affect their relative ordering. Refer to the same upstream manual before relying on order-dependent diagnostics.

What systemd-cat cannot promise

Writing a message is not the same as ensuring durable storage. The journal may be configured for volatile storage, and retention limits can remove older entries. The systemd-journald documentation explains journal storage and lifecycle. Never place API tokens, private keys, passwords or sensitive customer records into demonstration log entries.

Linux technicians can combine journal filtering with read-only system inspection. Linux Command #68 maps service process trees, #67 samples cgroup resource usage, and #65 examines boot timing. None of those observations alone establishes why a service failed.

Practice and verification

In an approved Linux test environment, create two messages with different priorities, then query only warnings. Note the journal identifier, actual priority and observed timestamp. Compare the results against the manual before writing a short diagnostic report. No service restarts, configuration changes or removal of journal files are needed.

Takeaway: systemd-cat connects command output or pipeline text to journald, while journalctl retrieves it. A useful troubleshooting exercise verifies both sides without mistaking a log entry for proof of hardware condition or guaranteed delivery.
