OSC.006 introduces C functions as named, reusable units of program behavior. A function can accept typed arguments, perform calculations or effects, and optionally return a value. Functions make large programs more understandable because a caller needs to know the function's contract without repeatedly rewriting its implementation. For systems programming, clear interfaces also provide an important boundary for reviewing assumptions, testing arithmetic, and controlling which symbols are visible to other source files.

The sequence follows OSC.005 on loops, OSC.004 on decisions, and OSC.003 on expressions. Students will reuse a for loop and if statements inside functions before advancing to pointers, arrays, dynamic memory, and more complex interfaces. Code examples target ISO C11, avoiding language-specific compiler extensions.

Learning Objectives and Prerequisites

  • Distinguish a declaration or prototype from a definition and a function call.
  • Identify a function's return type, name, formal parameters, call arguments, and return statement.
  • Write int and void functions and forward declarations with (void) when there are no parameters.
  • Explain why normal C function arguments are passed by value, and why a parameter can change without changing the caller's variable.
  • Explain block scope, automatic local variables, file-scope static functions, and prototypes in a header.
  • Build and run a C11 program, compare its actual output with expected results, and test input boundaries.

Prerequisites: basic C syntax, arithmetic, conditional statements, loops, terminal navigation, and a working C compiler from OSC.001's compiler introduction. Equipment: a computer with GCC or another conforming C11 compiler, a plain-text editor, and a terminal. The examples were compiled with GCC 14.2.0 in a Linux environment; learners using Windows can use a GCC-capable shell or adapt the build steps to a supported C toolchain.

Why Functions Matter in Systems Engineering

C developed alongside early UNIX systems work on computers such as Digital Equipment Corporation's PDP-11. The important historical connection is that a small, compiled programming language allowed operating-system software to be organized into separate routines and source files. A function can be compiled into machine instructions and called from another function, subject to the compiler and linker. The exact machine instructions and calling convention vary by target architecture.

Modern compilers still use functions to organize device drivers, server code, command-line tools, and firmware. Although function calls are often associated with an execution stack, a language's observable behavior does not require one universal stack-frame layout. Compilers may optimize function calls, inline a function, or use architecture-specific registers. Therefore, avoid drawing definitive physical-memory conclusions from a source-level explanation.

Function Declaration, Definition, and Call

A function declaration introduces its name and type. A declaration with parameter type information is commonly called a prototype. A definition includes the statements that implement the function. A call supplies argument expressions and transfers execution into the function. The name add below has two int parameters and returns int. Parameter names in a prototype are optional; they are required for parameter variables used in the definition.

int add(int left, int right);   /* prototype */

int add(int left, int right)    /* definition */
{
    return left + right;
}

/* Calling add(10, 20) produces the int value 30. */

A forward declaration is especially helpful if main calls a function defined below it. Standard C11 does not support implicit function declarations as valid modern practice. If a function takes no arguments, write int main(void) or int reset(void). In C11, an empty parameter list in a declaration has different historical meaning from a full no-argument prototype; later C standards have changed portions of that syntax. Using (void) is explicit and portable for the lesson.

A Complete C11 Program with Three Functions

The following program combines a loop-based summation, a bounded percentage, and an output-only function. The static keyword at file scope gives the helper functions internal linkage: code in another separately compiled source file cannot refer to the same symbols as externally linked functions. The demonstration deliberately uses small integer values so that signed integer overflow is not possible for the shown calls.

#include <stdio.h>

static int sum_inclusive(int first, int last);
static int clamp_percent(int value);
static void show_results(int sum, int percent);

int main(void)
{
    int sum = sum_inclusive(1, 5);
    int bounded = clamp_percent(125);
    show_results(sum, bounded);
    return 0;
}

static int sum_inclusive(int first, int last)
{
    int total = 0;
    for (int n = first; n <= last; ++n) {
        total += n;
    }
    return total;
}

static int clamp_percent(int value)
{
    if (value < 0) {
        return 0;
    }
    if (value > 100) {
        return 100;
    }
    return value;
}

static void show_results(int sum, int percent)
{
    printf("sum(1..5) = %d\n", sum);
    printf("clamped(125) = %d%%\n", percent);
}

Save the source as lesson06.c. Compile in a GCC-capable shell with the warning flags below. The -std=c11 option selects C11; -Wall, -Wextra, and -Wpedantic request diagnostic families; -Werror makes emitted warnings fail the build. Those switches are documented in the GCC warning-options manual. Compiler flags diagnose many issues but do not prove freedom from all runtime defects.

gcc -std=c11 -Wall -Wextra -Wpedantic -Werror lesson06.c -o lesson06
./lesson06

Verified output from GCC 14.2.0:

sum(1..5) = 15
clamped(125) = 100%

The code is a teaching exercise rather than a general integer-range library. For large or untrusted first and last values, a robust summation routine must address invalid ranges, arithmetic overflow, and loop termination. Additional input validation belongs at the function boundary instead of being assumed safe because a classroom run succeeded.

Parameters Are Passed by Value

In ordinary C function calls, parameter objects receive the values of the corresponding argument expressions. Changing a parameter's local integer does not modify the caller's separate integer variable. Later pointer lessons will show how copying a pointer value allows a function to access caller-owned storage. That mechanism is sometimes informally described as pass-by-reference, but C's actual argument passing remains by value.

#include <stdio.h>

static void add_five(int number)
{
    number += 5;
    printf("inside = %d\n", number);
}

int main(void)
{
    int original = 10;
    add_five(original);
    printf("outside = %d\n", original);
    return 0;
}

The tested program printed inside = 15 followed by outside = 10. The expression number += 5 changes the parameter variable only. If a caller needs a modified value, a useful beginner pattern is to return the computed value and assign it explicitly, as in original = add_five_and_return(original);, where a separately defined function returns an int. Do not assume that an argument becomes mutable in its caller merely because the callee changes a similarly named variable.

Block Scope, Function Linkage, and Storage Duration

A variable declared inside a block is visible from its declaration until the end of that block, subject to shadowing rules. An uninitialized automatic local integer has an indeterminate value and must not be read as though it were initialized to zero. The GNU C manual on local variables explains that local names and storage duration are different concepts; optimized machines do not necessarily allocate every local value in a physical stack slot.

  • Block-scope automatic variable: an ordinary local such as int total = 0; exists for its relevant block execution and has no meaningful value before initialization.
  • File-scope static function: a declaration such as static int clamp_percent(int value); names a helper with internal linkage for its translation unit.
  • Static local variable: a separate construct, static int count = 0; inside a function, retains stored state between calls even though its name is only visible in its block.
  • Global data: external-linkage file-scope objects can create shared mutable state; prefer explicit interfaces and small, testable functions when possible.

Avoid the claim that static always means one behavior. At file scope it can determine linkage; at block scope it changes an object's storage duration. Likewise, a function declared inside another function does not permit a nested definition in standard C11; nested function definitions are a GNU extension and are excluded from the portable examples.

Separate Compilation and Header Prototypes

As programs grow, definitions may reside in one C file while callers reside in another. An ordinary header can provide a shared declaration, reducing the risk that the caller assumes the wrong type. Create three small files in the same directory; the header guard prevents repeated inclusion of its declarations within one translation unit.

File metrics.h

#ifndef METRICS_H
#define METRICS_H

int square_small(int value);

#endif

File metrics.c

#include "metrics.h"

int square_small(int value)
{
    return value * value;
}

File multi_main.c

#include <stdio.h>
#include "metrics.h"

int main(void)
{
    printf("square_small(7) = %d\n", square_small(7));
    return 0;
}

The code was compiled and linked using both source files, not by separately executing a header. The command and observed output are:

gcc -std=c11 -Wall -Wextra -Wpedantic -Werror multi_main.c metrics.c -o modular
./modular
square_small(7) = 49

A source file can include a header for the same function it defines, enabling the compiler to compare declared types with the definition. When a function should be private to metrics.c, use a file-scope static definition and do not put a public prototype for it in metrics.h. The shown square_small is intentionally public between the two files. Multiplying arbitrary large signed integers can overflow; the example is safe for the tested value 7, not for all possible int inputs.

Embedded Applications and Hardware Context

Small microcontrollers often run programs written in C or related compiled languages. A function might read an input, limit a control value, compute a checksum, or update a state machine. Writing such tasks as testable functions separates algorithmic logic from hardware register access. Arduino sketches ordinarily use an Arduino C++-based build environment rather than pure ISO C11; therefore an Arduino board photograph demonstrates relevant hardware, not proof that a pure C11 file ran unchanged on the device.

Students who want a follow-on engineering context can compare the OSFTC.016 firmware clock-diagnostics lesson with the present focus on interfaces. In a real embedded system, timing, register volatility, concurrency and memory-mapped hardware introduce requirements beyond an introductory host-side function exercise.

Common Errors and Troubleshooting

  • Implicit or conflicting declaration: a function is called before a matching prototype is visible. Add the correct declaration, include the right header, and rebuild with warnings.
  • Undefined reference at link time: the caller compiles, but the object file defining the function was omitted or the symbol is not externally visible. Include the required source/object file and check linkage.
  • Return-type mismatch: a void function is used like an integer-valued function or a return expression has an incompatible type. Align the prototype, definition and caller.
  • Missing return value: a non-void path falls through without returning a usable value. Return a value along every reachable path that requires one.
  • Stale state assumption: a local variable is treated as persistent between independent calls. Distinguish automatic locals from explicitly declared static locals.
  • Wrong answer despite compilation: a tested range is invalid or integer arithmetic exceeds the type. Validate preconditions and use appropriate numeric types and checked arithmetic.
  • Misleading portability claim: an example uses GCC-only nested functions or relies on one ABI's stack layout. Stay within standard C11 interfaces.

Hands-On Exercises

  1. Compile lesson06.c with the documented strict C11 command and confirm the sum and clamping output.
  2. Change sum_inclusive(1, 5) to sum_inclusive(1, 10). Before running, predict the return value. Expected sum: 55.
  3. Call clamp_percent(-7), clamp_percent(65), and clamp_percent(120). Expected values: 0, 65, 100.
  4. Predict the output of the by-value program before compiling it. Explain why the caller still contains 10.
  5. Move a function definition beneath main but keep its prototype above main. Observe why compilation succeeds.
  6. Try compiling the multi-file example with only multi_main.c. Observe the missing definition at link time, then rebuild with metrics.c. Do not mistake a deliberate link failure for a compiler crash.

For a repeatable assertion exercise, create an additional file named test_functions.c containing the function implementations and assert calls. An assert program exits successfully when its active assertions hold; however, the NDEBUG macro disables assertions, so assertions must not substitute for production input validation. Five checks passed on GCC 14.2.0 in the controlled test environment.

#include <assert.h>

static int sum_inclusive(int first, int last) {
    int total = 0;
    for (int n = first; n <= last; ++n) total += n;
    return total;
}

static int clamp_percent(int value) {
    if (value < 0) return 0;
    if (value > 100) return 100;
    return value;
}

int main(void) {
    assert(sum_inclusive(1, 5) == 15);
    assert(sum_inclusive(5, 5) == 5);
    assert(clamp_percent(-8) == 0);
    assert(clamp_percent(73) == 73);
    assert(clamp_percent(125) == 100);
    return 0;
}

Build with gcc -std=c11 -Wall -Wextra -Wpedantic -Werror test_functions.c -o test_functions and run ./test_functions. A successful run produces no standard output and exits with status 0. The five checks passed in the recorded test; students should add a failing assertion only in a disposable exercise to learn how diagnostics differ from actual program output.

Knowledge Check and Answers

  1. What is a prototype? A function declaration specifying its callable type, including return and parameter types.
  2. How does a definition differ? It supplies the executable function body.
  3. What does void mean in int reset(void)? The function takes no arguments and returns an int.
  4. What does static mean for a helper function at file scope? It gives the function internal linkage within its translation unit.
  5. Why does the caller retain 10 after passing an integer to add_five? The callee changes its own parameter copy.
  6. Which values return from clamp_percent(-7) and clamp_percent(120)? 0 and 100.
  7. How does a header help? It shares consistent function declarations across source files.
  8. What causes an undefined-reference linker diagnostic? A required externally linked definition may be missing from the link or inaccessible under its linkage.
  9. Are all ordinary local integers initialized to zero? No. Uninitialized automatic locals have indeterminate values.
  10. Does a clean warning-enabled build prove security? No. Runtime assumptions, integer ranges, input validation and integration still require verification.

Conclusion

Functions turn repeated control-flow steps into reusable program interfaces. At the introductory level, the central engineering habits are to declare types explicitly, separate interface from implementation, initialize local variables, understand pass-by-value behavior, return coherent results and compile with meaningful diagnostics. The next progression can introduce C arrays and pointers without skipping the prerequisite distinction between a value and the storage that holds it.
