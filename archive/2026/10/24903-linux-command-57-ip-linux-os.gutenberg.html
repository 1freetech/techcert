The ip command is the central Linux networking tool for inspecting and changing interfaces, addresses, routes, and neighbor tables. It belongs to the iproute2 toolset and replaces many tasks that older administrators performed with ifconfig, route, and arp.

This lesson follows Linux Command #56 – ethtool. ethtool looks closely at the physical and driver-level behavior of a network interface card. The ip command moves one layer outward and shows how the Linux kernel sees the interface, its IP addresses, its default gateway, its routes, and the neighboring hosts it has learned.

Why the ip Command Matters

A Linux host can have multiple physical interfaces, virtual interfaces, bridges, VLAN interfaces, loopback interfaces, tunnels, and container networking devices at the same time. Each interface can have multiple IPv4 and IPv6 addresses, different routing rules, and different neighbor entries. The ip command provides one consistent interface for reading and changing that kernel networking state.

The upstream manual defines ip as a tool to show or manipulate routing, network devices, interfaces, and tunnels. Common objects include address, link, route, neighbor, rule, netns, and tunnel. For technician work, the most important starting points are ip addr, ip link, ip route, and ip neigh.

Learning Objectives

  • Identify Linux network interfaces and their administrative state.
  • Read IPv4 and IPv6 addresses with ip addr.
  • Use brief output to quickly inventory a host.
  • Read the routing table and identify the default route.
  • Use ip route get to see which path Linux will choose for a destination.
  • Read the neighbor table and interpret common neighbor states.
  • Distinguish link state, address state, route state, and DNS state.
  • Recognize when an ip change is temporary and may disappear after reboot.
  • Use read-only commands first before modifying a production host.

Start With ip -br addr

For a fast host inventory, run ip -br addr. The -br option requests brief output. The upstream manual documents brief mode for address, link, and neighbor views. A technician can quickly see interface names, whether the interfaces are up or down, and the addresses assigned to each one.

This is often the fastest answer to the question “What addresses does this Linux server currently have?” It is also useful when the machine has predictable interface names such as enp1s0, ens192, or eno1 rather than the older eth0 style.

ip addr Shows Address State

ip addr shows protocol addresses assigned to interfaces. You may see an IPv4 address such as 192.168.10.24/24, an IPv6 link-local address beginning with fe80::, and one or more globally usable IPv6 addresses. Review IPv6 addressing and Neighbor Discovery when interpreting multiple IPv6 addresses on one interface.

The prefix length after the slash is part of the address. For IPv4, /24 means the first 24 bits define the network prefix. That connects directly to the earlier lesson on subnet masks.

If a client receives an address dynamically, the output may include a dynamic flag. That can support a DHCP troubleshooting investigation, although the ip command by itself does not replace the lease manager, NetworkManager, systemd-networkd, or other configuration service that owns the persistent settings.

ip link Shows the Device Layer

ip link focuses on the network-device layer. It shows interfaces, MAC addresses, MTU values, queue state, and flags such as UP, LOWER_UP, and NO-CARRIER. These clues help separate a physical-link problem from an IP-address problem.

If an interface is administratively up but has no usable carrier, compare the result with ethtool and the networking lesson on Ethernet link negotiation. ip link tells you what the kernel believes about the interface state; ethtool can expose negotiated speed, duplex, driver details, and NIC statistics.

Read-Only First, Changes Second

On a production server, begin with read-only commands. Commands such as ip addr, ip link, ip route, and ip neigh are safe inspection tools. Commands using verbs such as add, del, replace, or set change kernel networking state and can immediately disconnect a remote session.

For example, sudo ip link set dev enp1s0 down administratively disables that interface. Running it over SSH through that same interface can terminate your connection. The same caution applies to removing an address or replacing a default route.

ip route Shows How Linux Reaches Other Networks

ip route displays the routing table. A typical host may have a default route through a router plus one or more directly connected routes created automatically for local subnets. The lesson on static routing and longest-prefix match explains how routers and hosts choose among competing routes.

A line such as default via 192.168.10.1 dev enp1s0 means destinations without a more specific matching route normally leave through enp1s0 and use 192.168.10.1 as the next-hop router.

ip route get Is an Excellent Troubleshooting Tool

ip route get DESTINATION asks the kernel which route it would select for a specific destination. On multihomed systems, VPN-connected machines, containers, and servers with multiple addresses, this is often more useful than simply reading the entire table.

The result can show the selected next hop, output interface, and source address. That makes it valuable when a server reaches the internet through the wrong interface, chooses an unexpected source address, or returns traffic through a different path than expected.

ip neigh Replaces the Old ARP View

ip neigh shows the kernel’s neighbor table. For IPv4, this includes the information traditionally associated with the ARP table: an IP address, the corresponding link-layer address, the interface, and a neighbor state. For IPv6, the same framework supports Neighbor Discovery.

Common states include REACHABLE, STALE, DELAY, PROBE, INCOMPLETE, and FAILED. A failed neighbor entry can point to a local Layer 2 problem, incorrect VLAN placement, an unavailable target, or filtering that prevents address resolution.

Statistics With ip -s link

ip -s link adds interface statistics such as received and transmitted packets, bytes, drops, errors, and other counters. These numbers can help identify a local interface that is accumulating errors or dropping traffic.

Do not interpret counters in isolation. A nonzero error total accumulated over months may be less important than a counter rising rapidly during the current incident. Compare timestamps, traffic volume, switch-side counters, and ethtool statistics before deciding which layer is actually failing.

Useful Display Options

  • ip -br addr — compact interface and address summary.
  • ip -br link — compact link-state summary.
  • ip -c addr — colorized output in a terminal.
  • ip -4 addr — show IPv4 address information.
  • ip -6 addr — show IPv6 address information.
  • ip -s link — show interface statistics.
  • ip -j addr — output address data as JSON for scripts or automation.

The JSON output option is especially useful when building reliable automation. Parsing human-oriented terminal text with fragile regular expressions is usually less robust than consuming structured output.

Temporary Changes vs. Persistent Configuration

The ip command changes the kernel’s current networking state. On many Linux distributions, a manual address or route added with ip does not automatically become persistent across reboot. Persistent networking may be managed by NetworkManager, systemd-networkd, Netplan, distribution-specific configuration files, a cloud-init system, or an orchestration platform.

That distinction matters during troubleshooting. A temporary command can be useful for a controlled test, but a successful temporary fix is not complete until the persistent configuration is corrected in the system that owns it.

A Practical Troubleshooting Sequence

  1. Run ip -br link and confirm the expected interface exists.
  2. Run ip -br addr and confirm the expected IPv4 and IPv6 addresses.
  3. Check ip route for the default route and connected networks.
  4. Use ip route get DESTINATION to see the kernel’s actual path choice.
  5. Check ip neigh when a same-subnet host or gateway cannot be reached.
  6. Use ip -s link for interface errors and drops.
  7. Compare physical-link evidence with ethtool.
  8. Use ping and ICMP only after confirming local interface, address, and route state.
  9. Use traceroute or related path tools when the local route is correct but remote reachability still fails.
  10. Check DNS only after proving basic IP connectivity.

Common Failure Patterns

  • Interface exists but is DOWN: investigate administrative state, service ownership, or intentional shutdown.
  • Interface is UP but has no expected address: investigate DHCP, static configuration, NetworkManager, systemd-networkd, Netplan, or the owning service.
  • Address is correct but there is no default route: remote networks may be unreachable even though local subnet traffic works.
  • Default route exists but uses the wrong interface: inspect metrics, policy routing, VPN state, and competing routes.
  • Gateway address exists but neighbor state is FAILED: investigate Layer 2 reachability, VLAN assignment, switching, or gateway availability.
  • Packets leave through an unexpected source address: use ip route get to verify the kernel’s route and source-address selection.
  • Manual fix disappears after reboot: update the persistent network configuration rather than relying on a one-time ip command.

Hands-On Exercise

On a Linux system you control, run ip -br link, ip -br addr, ip route, and ip neigh. Record the active interface name, MAC address, IPv4 address, IPv6 address, default gateway, and at least one neighbor entry.

Next, choose a permitted remote IP address and run ip route get DESTINATION. Record the output interface, next hop if present, and selected source address. Finish by running ip -s link and noting whether any receive or transmit error counters are increasing. Do not add, remove, or replace addresses or routes during this exercise.
