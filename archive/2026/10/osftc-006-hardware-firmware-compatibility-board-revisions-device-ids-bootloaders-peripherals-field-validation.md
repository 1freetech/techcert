<!-- wp:heading --><h2 class="wp-block-heading"><strong>Elementary Overview</strong></h2><!-- /wp:heading -->
<!-- wp:paragraph --><p><strong>Hardware/firmware compatibility</strong> means proving that a specific <a href="https://bitcoinversus.tech/2026/10/04/osfec-001-microcontroller-architecture-memory-maps-registers-interrupts/"><strong>microcontroller</strong></a> board can safely run a specific firmware image. The filename alone is not enough. A technician should identify the exact board revision, processor or device ID, <a href="https://bitcoinversus.tech/2026/10/08/osfec-005-bootloader-design-firmware-update-architecture-image-validation-ab-slots-rollback-versioning-recovery/"><strong>bootloader</strong></a> version, memory layout, peripheral configuration, and required hardware options before flashing. A firmware image may be valid for one revision and wrong for another even when the boards look almost identical. This lesson builds directly on safe <a href="https://bitcoinversus.tech/2026/10/04/osftc-001-firmware-images-safe-flashing-bootloaders-recovery-basics/"><strong>firmware images and recovery</strong></a>, <a href="https://bitcoinversus.tech/2026/10/05/osftc-002-serial-console-boot-logs-uart-baud-rate-pinouts-capture-recovery/"><strong>serial-console boot logs</strong></a>, <a href="https://bitcoinversus.tech/2026/10/05/osftc-003-firmware-backup-recovery-checksums-golden-images-rollback-validation/"><strong>checksums and rollback</strong></a>, and <a href="https://bitcoinversus.tech/2026/10/06/osftc-004-firmware-flashing-interfaces-usb-dfu-swd-jtag-spi-programmers-bootloader-modes-write-verification/"><strong>USB DFU, SWD/JTAG, and SPI flashing</strong></a>.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>The Compatibility Layers</strong></h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Think of compatibility as a chain: <strong>Compatible = processor match AND board-revision match AND memory-map match AND bootloader contract match AND peripheral-map match.</strong> A change at any layer can matter. A later board revision may move a GPIO, replace a sensor, use a different <a href="https://bitcoinversus.tech/2026/10/06/easy-tech-read-what-is-a-device-driver-how-hardware-talks-to-the-operating-system/"><strong>device driver</strong></a>, change the oscillator, alter external <a href="https://bitcoinversus.tech/2025/04/10/ram-vs-flash-memoryssd-usb-memory-cards/"><strong>flash memory</strong></a>, or reserve a different region for the bootloader. Modern embedded platforms often keep those hardware facts in board-support files or a Devicetree so the software knows what physical hardware exists. For a technician, the lesson is simple: never assume two boards are interchangeable because the enclosure, connector, or product name is the same.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Identify the Exact Hardware Before Flashing</strong></h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Before changing firmware, collect identity evidence from the device itself and from the approved service documentation. Useful identifiers include the product model, PCB revision, assembly number, MCU part number, silicon revision, unique device ID, installed bootloader version, current application version, and programmer-detected target. If the tool reports a different chip than the work order expects, stop and investigate. This is where production programming software is valuable: it can identify a target, read memory, program an image, and verify the write instead of relying on a handwritten label. The same discipline applies whether the connection uses <a href="https://bitcoinversus.tech/2025/04/11/usb-standards-speeds-connectors-and-compatibility/"><strong>USB</strong></a>, SWD, JTAG, SPI, or another service interface.</p><!-- /wp:paragraph -->

<!-- wp:list --><ul class="wp-block-list"><li><strong>Board identity:</strong> model, PCB revision, assembly revision, serial number.</li><li><strong>Processor identity:</strong> exact MCU/SoC part number, package, silicon stepping or revision.</li><li><strong>Firmware identity:</strong> application version, build ID, release channel, checksum or signed-image identifier.</li><li><strong>Boot identity:</strong> bootloader version, recovery mode, partition or slot layout.</li><li><strong>Peripheral identity:</strong> sensors, radios, storage devices, displays, GPIO assignments, buses, and external memory.</li><li><strong>Programming identity:</strong> programmer/debugger model, detected target, interface voltage, connection method, and tool version.</li></ul><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Verify the Image and Toolchain</strong></h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>A compatibility check should verify both the image and the tool used to install it. Confirm the approved filename, version, target family, release notes, file size, and cryptographic hash before programming. On Linux, a technician can use <code>sha256sum firmware.bin</code>; in Windows PowerShell, <code>Get-FileHash .\firmware.bin -Algorithm SHA256</code> provides the same kind of evidence. The expected digest should come from a trusted release record, not from the same unverified file being checked. If the firmware package includes a machine-readable manifest, <a href="https://bitcoinversus.tech/2026/10/08/it-what-is-json-javascript-object-notation-structured-data/"><strong>JSON</strong></a> is a common format for fields such as board ID, minimum bootloader version, image version, memory address, and checksum.</p><!-- /wp:paragraph -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Board-Specific Settings Can Break a Good Firmware Image</strong></h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>Even when the main application binary is correct, device configuration can still make a board fail. Option bytes, fuses, security bits, flash-protection settings, boot pins, external-memory loaders, clock configuration, and boot addresses can all be board-specific. A technician should therefore preserve or record configuration before altering it and should never copy low-level settings from a different board revision unless the approved procedure says they are identical. The same caution applies to <a href="https://bitcoinversus.tech/2026/10/06/osfec-004-linker-scripts-startup-code-memory-sections-vector-tables-stack-heap-map-files/"><strong>memory sections, vector tables, stack, heap, and linker maps</strong></a>: firmware can compile successfully yet still be built for the wrong memory organization.</p><!-- /wp:paragraph -->

<!-- wp:list --><ul class="wp-block-list"><li><strong>Clocking:</strong> crystal frequency, internal/external clock source, PLL assumptions.</li><li><strong>Boot configuration:</strong> boot address, boot pins, active slot, recovery partition.</li><li><strong>Memory:</strong> internal flash size, external NOR/NAND, RAM map, reserved bootloader space.</li><li><strong>Peripherals:</strong> I²C/SPI addresses, UART assignment, GPIO polarity, sensor model, display controller.</li><li><strong>Protection:</strong> readout protection, secure boot, write protection, debug access, signed-image requirements.</li></ul><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Field Validation After Flashing</strong></h2><!-- /wp:heading -->
<!-- wp:paragraph --><p>A successful “program complete” message only proves that bytes were written; it does not prove that the device is fully compatible or functional. After flashing, boot the device and validate the whole expected path: correct version banner, normal <a href="https://bitcoinversus.tech/2026/10/05/osftc-002-serial-console-boot-logs-uart-baud-rate-pinouts-capture-recovery/"><strong>boot log</strong></a>, no unexpected <a href="https://bitcoinversus.tech/2026/10/07/osftc-005-watchdog-timers-reset-loops-timeouts-feeding-reset-causes-firmware-troubleshooting/"><strong>watchdog resets</strong></a>, correct network or bus initialization, recognized storage, working sensors, expected outputs, and a controlled reboot. For a batch of identical units, automate the repeatable steps where possible but keep a traceable record of target identity, image identity, verification result, and final functional test. A failure that appears only on one board revision is a strong clue that the problem is compatibility rather than a universally bad image.</p><!-- /wp:paragraph -->

<!-- wp:list {"ordered":true} --><ol class="wp-block-list"><li>Confirm the flashed version or build ID.</li><li>Capture the first complete boot after programming.</li><li>Confirm reset cause is normal.</li><li>Test all required communication interfaces.</li><li>Verify external storage and attached peripherals.</li><li>Exercise one normal shutdown/restart or power-cycle sequence.</li><li>Confirm the device returns to service without recovery mode.</li><li>Record pass/fail, board revision, firmware version, and technician evidence.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Practical Compatibility Example</strong></h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol class="wp-block-list"><li>A work order says to install firmware <strong>3.7.2</strong> on Product X.</li><li>The service matrix says 3.7.2 supports board revisions <strong>B and C</strong>, MCU family <strong>M4</strong>, and bootloader <strong>1.4 or later</strong>.</li><li>The technician reads the target and finds board revision <strong>A</strong> with bootloader <strong>1.2</strong>.</li><li>The correct action is <strong>do not flash</strong>. The mismatch is proven before the device is put at risk.</li><li>If the board is revision C with bootloader 1.5, the technician verifies the image hash, programs it, checks boot logs, and completes the functional test.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Technician Workflow</strong></h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol class="wp-block-list"><li>Photograph or record the board label and PCB revision.</li><li>Read the exact MCU/SoC identifier with an approved tool.</li><li>Record current application and bootloader versions.</li><li>Back up configuration or firmware when the service procedure requires it.</li><li>Match board revision and processor against the approved compatibility matrix.</li><li>Verify the firmware filename, version, size, and SHA-256 hash.</li><li>Confirm programmer/debugger tool version and interface settings.</li><li>Record board-specific option bytes, fuses, or protection settings before changing them.</li><li>Program the image using the approved interface.</li><li>Run read-back or tool-level verification where supported.</li><li>Capture the first boot and confirm the expected version and reset cause.</li><li>Test required peripherals and communications before returning the device to service.</li><li>If the unit fails, compare the failure against another known-good unit of the <strong>same hardware revision</strong>.</li><li>Use the <a href="https://bitcoinversus.tech/2026/10/05/osftc-003-firmware-backup-recovery-checksums-golden-images-rollback-validation/"><strong>golden image or rollback path</strong></a> if the approved recovery criteria are met.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Knowledge Check + Answers</strong></h2><!-- /wp:heading -->
<!-- wp:list {"ordered":true} --><ol class="wp-block-list"><li><strong>What is hardware/firmware compatibility?</strong> A proven match between the firmware image and the exact processor, board revision, bootloader, memory layout, peripherals, and required configuration.</li><li><strong>Why read the device ID?</strong> To prove which target chip is physically present rather than relying on labels or assumptions.</li><li><strong>What does a SHA-256 hash prove?</strong> That the file being used matches the expected byte content when its digest matches a trusted reference.</li><li><strong>Why can a board revision matter?</strong> A revision can change pins, clocks, memory, sensors, power behavior, or other hardware assumptions used by firmware.</li><li><strong>What should happen if the detected target does not match the approved compatibility matrix?</strong> Stop the flash and investigate.</li><li><strong>Does “program verified” mean the complete device passed?</strong> No. It proves the programmed data matched the write operation; functional validation is still required.</li><li><strong>What is the safest comparison unit for troubleshooting a revision-specific failure?</strong> A known-good device with the same hardware revision and approved firmware.</li></ol><!-- /wp:list -->

<!-- wp:heading --><h2 class="wp-block-heading"><strong>Elementary Review</strong></h2><!-- /wp:heading -->
<!-- wp:list --><ul class="wp-block-list"><li>Read the hardware identity first.</li><li>Match the exact board and processor to the approved firmware.</li><li>Check the bootloader and memory requirements.</li><li>Verify the file hash before programming.</li><li>Preserve board-specific settings.</li><li>Verify the write.</li><li>Boot the device and test the real hardware.</li><li>Document exactly what passed or failed.</li><li>If the identity does not match, stop rather than guessing.</li></ul><!-- /wp:list -->
