Asyncio logging is not mainly about making the logging API itself asynchronous. The core engineering problem is preventing slow log handlers—especially file and network handlers—from blocking Python’s asyncio event loop. A healthy design lets coroutines create LogRecord objects quickly, then moves potentially blocking log output away from the event-loop thread.

This lesson follows OSPython.039: Logging with ProcessPoolExecutor. That lesson dealt with multiple processes. OSPython.040 focuses on asyncio, where many concurrent tasks often share one event-loop thread and therefore must avoid blocking operations.

Elementary Overview

An asyncio Task runs until it reaches an operation that yields control with await. The event loop can then run another task. This cooperative model works well only when code avoids long synchronous pauses. A normal logging call looks small, but a handler may write to disk, send data over a socket, flush a stream, rotate a file, or perform formatting work before returning.

Python’s current Logging Cookbook specifically warns that file and network handlers can create problems in asynchronous applications because they may block the event loop. It recommends the queue-based approach already introduced in OSPython.037: QueueHandler and QueueListener.

Learning Objectives

  • Use QueueHandler and QueueListener to move blocking output off the event-loop thread.
  • Add task, request, or correlation context to asynchronous log records.

  • Understand the difference between task cancellation and ordinary application errors.
  • Shut down queues and listeners without silently losing final log messages.
  • Recognize when logging volume or formatting work itself becomes a performance problem.
  • Build an evidence-based logging configuration for production asyncio services.

The Event Loop Must Stay Responsive

The event loop schedules ready callbacks and tasks. If one task performs a blocking operation for 200 milliseconds, other ready tasks may wait behind it even though they are logically independent. This is why time.sleep() is harmful inside coroutine code while await asyncio.sleep() cooperates with the scheduler.

Logging can create the same pattern. A FileHandler, network handler, or custom handler may perform blocking I/O. The call to logger.info() is synchronous from the coroutine’s perspective, so the coroutine cannot yield until the handler finishes.

QueueHandler Separates Log Creation From Log Output

A QueueHandler places a log record onto a queue instead of writing the final output itself. A QueueListener runs separately, removes records from that queue, and passes them to real output handlers such as console, file, rotating-file, or network handlers.

The important boundary is architectural: the event-loop thread should do as little logging work as practical, while the listener thread performs slower handler work. Python’s documentation explicitly recommends this pattern when asynchronous code is present so blocking handler work occurs in the QueueListener thread rather than in the event loop.

A Minimal Async-Safe Architecture

  1. Create a standard thread-safe queue.Queue.
  2. Attach logging.handlers.QueueHandler to the application logger or root logger.
  3. Create the real destination handler, such as StreamHandler or FileHandler.
  4. Create a QueueListener using the queue and destination handler.
  5. Start the listener before the asyncio workload begins.
  6. Run the application with asyncio.run().
  7. During shutdown, wait for important tasks to complete or cancel them deliberately.
  8. Stop the QueueListener so queued records can finish processing.

Python 3.14 added context-manager support to QueueListener, allowing it to start when entering a with block and stop when leaving the block. The older explicit start() and stop() methods remain important to understand because many deployed Python versions and existing applications still use them.

Do Not Replace QueueHandler With asyncio.Queue

An asyncio.Queue is designed for coordination among asyncio tasks and is not thread-safe. logging.handlers.QueueHandler expects a queue-like object with synchronous queue methods such as put_nowait(). For the standard QueueHandler/QueueListener design, use the queue type expected by the logging implementation, typically queue.Queue.

This distinction matters because the listener normally runs in a separate thread. The queue is the bridge between synchronous logging calls made by event-loop tasks and the listener thread that performs output.

Add Context So Concurrent Tasks Can Be Distinguished

Concurrency makes logs harder to read because events from different tasks are interleaved. A useful record should identify which request, job, device, user operation, or task produced it. The techniques from OSPython.034: Contextual Logging with LoggerAdapter and extra still apply.

For example, a web service may add request_id, client_ip, or route. A data-collection service may add device_id, site, or poll_cycle. A worker may add a job identifier. The objective is to make one task’s records traceable even when hundreds of other tasks are logging at the same time.

Context Variables Work Well With Asyncio

Python’s contextvars module is designed for context-local state and works naturally with asyncio tasks. A ContextVar can carry a request or correlation identifier through an asynchronous call chain without forcing every function to pass that identifier manually as an argument.

A logging filter or adapter can read the current ContextVar and add it to each LogRecord. This creates task-aware logs while preserving the standard Python logging API.

Task Names Are Useful Diagnostic Metadata

Modern asyncio lets developers assign names to tasks. Inside coroutine code, asyncio.current_task() can identify the currently running task, and Task.get_name() returns its name. Descriptive task names such as poll-rack-12 or client-session-42 can make logs easier to correlate during failures.

Task names are supplemental context, not a replacement for durable identifiers. A request ID or job ID may be more useful across process restarts or distributed services.

Exceptions From Awaited Coroutines

When an awaited coroutine raises an exception, normal Python exception handling applies. Catch only errors you can handle meaningfully, and use logging.exception() or exc_info=True when a traceback is needed.

Avoid catching Exception around huge sections of the event loop simply to keep the program alive. Broad catches can hide programming errors and produce misleading “successful” task completion. Log the failure at the layer that owns recovery or escalation.

Background Tasks Need Explicit Failure Handling

A task created with asyncio.create_task() may run independently of the coroutine that created it. If its exception is never awaited or retrieved, asyncio can report that a task exception was never retrieved. Production designs should keep references to important tasks, await them through structured coordination such as TaskGroup, or attach carefully designed completion handling.

The log should identify the task, operation, and failure context. Recording only “Task failed” without the traceback or correlation ID makes post-incident analysis unnecessarily difficult.

Cancellation Is Not the Same as an Error

Async applications commonly cancel tasks during shutdown, timeout handling, failover, or request termination. asyncio.CancelledError represents cancellation semantics and should generally be allowed to propagate after any required cleanup. Treating every cancellation as an ERROR-level incident can flood logs during normal shutdown.

Choose log levels based on operational meaning. A planned task cancellation during deployment may be DEBUG or INFO. A timeout that violates an availability objective may be WARNING or ERROR. Logging level should communicate severity, not merely exception type.

Graceful Shutdown Must Include the Logging Pipeline

An async service often shuts down in stages: stop accepting new work, signal long-running tasks, await or cancel remaining tasks, close clients and sockets, then finish logging. If the process exits before the queue listener drains pending records, the final failure or shutdown messages can disappear.

For this reason, stopping the QueueListener is part of application lifecycle management. The final shutdown path should be deterministic and should not depend on the interpreter abruptly terminating background threads.

dictConfig Can Configure Queue-Based Logging

The configuration techniques from OSPython.036: Logging Configuration with dictConfig extend to queue-based designs. Python’s logging.config documentation describes direct QueueHandler/QueueListener configuration support added in Python 3.12.

This matters in production because logging topology can be changed without scattering handler construction throughout application code. A central configuration can define formatter behavior, output destinations, handler levels, and the queue/listener relationship.

Structured Logs Help Async Systems

Async services frequently process many similar operations concurrently. Structured fields make those operations easier to filter and aggregate. Useful fields can include timestamp, level, logger name, task name, request ID, operation, duration, destination, status code, exception type, and retry count.

The formatting principles from OSPython.032 and the contextual fields from OSPython.034 become more valuable as concurrency increases.

Measure Before Optimizing

Not every asyncio application needs an elaborate logging pipeline. A low-volume command-line tool writing occasional console messages may never experience measurable logging delay. A high-throughput server writing JSON records to disk or across a network may behave very differently.

Measure event-loop latency, application response times, queue depth, logging throughput, and handler latency before making performance claims. The goal is to remove actual blocking risk without adding unnecessary complexity.

Common Failure Patterns

  • Event loop periodically stalls: investigate synchronous file, socket, DNS, database, or custom logging handlers running in the loop thread.
  • Logs from many tasks are impossible to correlate: add request IDs, job IDs, task names, or ContextVar-based metadata.
  • Final shutdown messages disappear: verify task shutdown order and ensure the QueueListener is stopped cleanly.
  • Background task failures appear only as asyncio warnings: retain and await important tasks or use structured task groups.
  • Logging itself consumes excessive CPU: inspect formatter cost, stack traces, JSON serialization, filters, and excessive DEBUG volume.
  • Queue grows continuously: the listener or downstream handler cannot keep up with record production; reduce volume, improve handler throughput, or change the logging architecture.
  • Duplicate messages appear: check logger propagation and duplicate handlers, using the principles from logging hierarchy.

Hands-On Lab

Create a small asyncio program with three named tasks. Each task should log when it starts, before and after an await asyncio.sleep(), and when it completes. First configure a normal console handler and observe the interleaving of records.

Next, replace the direct output handler on the application logger with a QueueHandler. Create a QueueListener that owns the console handler. Run the same workload and confirm that log records still contain the originating task context while output work is handled away from the event loop.

Add a ContextVar called request_id and populate it differently for each task. Add the value to each LogRecord using a filter or adapter. Finally, make one task raise a controlled exception, log the traceback, then test graceful cancellation and shutdown. Verify that the last queued log message appears before the process exits.
