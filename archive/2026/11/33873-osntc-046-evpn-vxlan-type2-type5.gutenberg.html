OSNTC.046 explains why an endpoint can disappear from an Ethernet VPN (EVPN) fabric even while its physical link remains up. VXLAN carries tenant Ethernet traffic across a routed IP underlay. BGP EVPN distributes information about reachable MAC addresses, host IPs and routed prefixes. An operator therefore needs to check control-plane advertisements, overlay next hops and actual forwarding, not just port LEDs. The lesson extends OSNTC.045 on RoCEv2 congestion and OSDCEC.009 on data-center fabrics.

Type 2 carries MAC and optional host-IP reachability

EVPN Route Type 2, the MAC/IP Advertisement Route, announces a learned MAC address and can include an associated IP address. Leaf switches use it to discover remote endpoints without relying solely on traditional flood-and-learn behavior. An imported route still needs the correct tenant context, route target and reachable VXLAN tunnel endpoint (VTEP) to become useful for forwarding. Cisco's Nexus 9000 VXLAN configuration reference documents the EVPN route and MAC verification commands.

An endpoint may be locally learned but not exported, visible in BGP yet rejected by the remote import policy, or imported without a working underlay path. Those failure modes call for different evidence. Avoid declaring a server faulty merely because its MAC is absent from one switch's forwarding table.

Type 5 advertises IP prefixes

Route Type 5 advertises an IP prefix, commonly supporting routed connectivity between tenant subnets or toward an external network through an L3 VXLAN service. Unlike a host MAC/IP Type 2 advertisement, a Type 5 route describes prefix reachability without requiring a separate advertisement for every host MAC. Juniper's EVPN Type 5 explanation describes the separation. Type 2 and Type 5 can coexist, and vendor-specific route preferences may influence which path is installed.

A healthy Type 5 route does not prove a particular host's Type 2 information exists. An operator troubleshooting traffic must establish whether the failing destination is a local or remote MAC, a routed host, or an IP prefix reached through a border leaf. See OSNTC.024 on next hops and routing tables for the underlying forwarding concepts.

A safe, read-only verification sequence

For a supported Cisco Nexus NX-OS fabric, start by recording the platform, release, tenant VRF, VLAN-to-VNI mapping, intended source and destination, and incident timestamps. The following examples are observation commands; exact syntax and available output differ by switch family and software version. Confirm them against the local command reference before use.

show bgp l2vpn evpn summary
show bgp l2vpn evpn
show nve peers
show nve vni
show l2route evpn mac all
show l2route evpn mac-ip all

Check in order: BGP EVPN session state, expected Type 2 and Type 5 advertisements, VTEP peer status, membership in the correct VXLAN Network Identifier (VNI), then the learned local and remote MAC/IP entries. Cisco's EVPN troubleshooting guidance explicitly distinguishes host reachability from Type 5 external-prefix reachability. A BGP session alone is insufficient evidence of a usable data path.

Practice: one missing host, one healthy prefix

Fictional incident: Tenant BLUE has a remote server at 10.10.10.25, MAC 00:11:22:33:44:55, reached through VTEP 192.0.2.12. A routed Type 5 advertisement for 10.20.0.0/24 is visible, and the remote VTEP is reachable in the underlay. However, the expected server MAC/IP Type 2 advertisement is missing from the receiving leaf's EVPN table. All addresses and observations are teaching examples; no real network was queried.

Before selecting a repair, confirm whether the server MAC is learned on its attachment leaf. If yes, compare the originating and receiving BGP EVPN tables, tenant route targets, import/export policy and matching L2 VNI. If the Type 2 route is present in BGP but absent from the installed EVPN MAC table, investigate next-hop resolution and supported installation diagnostics. If no remote route exists at all, inspect the source of advertisement rather than changing receive-side forwarding indiscriminately.

For a Junos environment, comparable read-only observations include show route table bgp.evpn.0 and show evpn database. Juniper's official policy-filter example demonstrates both commands. Do not copy a Cisco command directly into Junos or assume identical tables and route preferences.

Where the underlay and overlay meet

VXLAN commonly uses UDP destination port 4789. The IP underlay must route packets to the remote VTEP; the EVPN control plane must distribute appropriate reachability; and tenant-specific VNI and routing contexts must agree. A working optical interface or 800G port does not guarantee either overlay requirement. Review OSNTC.044 on optics and FEC and OSNTC.043 on breakout mapping to separate physical failures from EVPN reachability faults.

Avoid changing route targets, VLAN mappings, BGP sessions, NVE interfaces or tunnel settings during an exploratory check. Such changes may disconnect many tenants. Record time-stamped output, affected endpoints and a narrow hypothesis. If configuration remediation is necessary, follow an approved change plan with peer review and rollback steps.

Lab questions and acceptance evidence

Explain why a received Type 5 route cannot substitute automatically for a missing Type 2 MAC/IP route. Identify which leaf should originate the missing announcement. List the read-only evidence that would distinguish a route export failure, import-policy mismatch and VTEP reachability issue. An acceptable lab report names the exact route, peer and tenant context for each conclusion, while labeling unverified claims explicitly.

Takeaway: Troubleshoot EVPN-VXLAN from endpoint to control plane to tunnel to forwarding table. Type 2 identifies MAC/IP reachability; Type 5 identifies IP prefixes. Correct classification prevents unnecessary changes to healthy ports or unrelated tenants.
