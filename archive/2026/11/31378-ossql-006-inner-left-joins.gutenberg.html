SQL JOIN combines rows from related database tables by evaluating a condition between their columns. Data-center inventories, manufacturing applications, business records and monitoring databases often separate equipment information from racks, facilities and other reference data. A foreign key can represent the relationship without repeating the entire rack description on every equipment record. OSSQL.006 explains how to retrieve matching data, preserve unmatched records, and avoid accidental row loss.

Why databases separate equipment from rack descriptions

A rack inventory can assign one numeric rack_id to each rack, while a miner record refers to that identifier. Storing a rack name and location only once reduces repeated text and supports consistent updates. A primary key identifies each rack row uniquely. A foreign key connects a device to an existing rack, or can remain NULL when the schema permits an unassigned device. The latter is a valid relationship state, not necessarily a corrupt record.

CREATE TABLE racks (
  rack_id INTEGER PRIMARY KEY,
  rack_name TEXT NOT NULL UNIQUE,
  location TEXT NOT NULL
);
CREATE TABLE miners (
  miner_id INTEGER PRIMARY KEY,
  model TEXT NOT NULL,
  rack_id INTEGER REFERENCES racks(rack_id),
  rated_hashrate_th INTEGER NOT NULL
);

The full laboratory file includes a positive-value CHECK constraint and an optional index on the child-side rack identifier. SQLite foreign keys must be explicitly enabled on each database connection unless configured otherwise; execute PRAGMA foreign_keys = ON; outside any open transaction and verify its value. A foreign-key declaration alone should not be assumed to enforce every reference. Consult the official SQLite foreign-key documentation.

The source provides four racks and seven miners. Rack A has two miners, Rack B has one, Rack C has two, and Rack D has none. Two miners deliberately have rack_id = NULL. The relationship is one rack to potentially many miners, so a rack's name may legitimately appear in more than one joined output row. The lab's data is synthetic, and the shown numerical rates are not measured.

INNER JOIN returns only matches

INNER JOIN, often written simply as JOIN, returns matching pairs of rows satisfying an ON expression. With the training data, five miners have a rack assignment. The two unassigned miners do not match any rack because an equality comparison involving SQL NULL is not true. Column qualification makes the query readable when identifiers have similar names in multiple tables.

SELECT m.miner_id, m.model, r.rack_name
FROM miners AS m
INNER JOIN racks AS r
  ON m.rack_id = r.rack_id
ORDER BY m.miner_id;

Observed test result: five rows, for miner IDs 1001, 1002, 1003, 1005 and 1006. Miner 1004 and 1007 do not appear. m and r are local table aliases; they do not rename the actual tables. The official PostgreSQL joins tutorial shows the same relational behavior with a weather-and-cities example. OSSQL.002 on SELECT and FROM provides more background on choosing result columns.

LEFT JOIN preserves the left-hand side

LEFT JOIN retains every left-side row at least once, even when no matching right-side record exists. Where no rack matches a miner, its rack columns are presented as NULL. The original miner fields remain present. A LEFT JOIN can still return more rows than its left table if a left record matches multiple right records; preserving left rows is not a promise of exactly one output row per record.

SELECT m.miner_id, m.model, r.rack_name
FROM miners AS m
LEFT JOIN racks AS r
  ON m.rack_id = r.rack_id
ORDER BY m.miner_id;

Observed test result: all seven miner records appear. Rows 1004 and 1007 have a NULL rack name. SQL NULL does not mean an empty string, zero, or a literal text value reading “NULL”; it means the queried value is missing or unknown. The SQLite SELECT reference explains when outer-join NULL values are added.

Finding unassigned equipment

A left anti-join pattern identifies left-side records that have no match on the right. It uses a LEFT JOIN followed by a check for a right-side non-nullable key. Since r.rack_id is the primary key, a null result for it demonstrates the missing match. Be careful when checking an optional right-side column instead: a matched row might contain a NULL in a nullable field.

SELECT m.miner_id, m.model
FROM miners AS m
LEFT JOIN racks AS r
  ON m.rack_id = r.rack_id
WHERE r.rack_id IS NULL
ORDER BY m.miner_id;

Observed test result: miner IDs 1004 and 1007. To find unused racks, reverse the roles: begin with racks AS r LEFT JOIN miners AS m, then filter on m.miner_id IS NULL. That returns Rack D in the sample. A real inventory query would need to define how it treats retired equipment, scheduled assignments, missing telemetry and inventory cutoffs, rather than inferring operational outages from a NULL relationship.

ON and WHERE are not interchangeable in an outer join

For an INNER JOIN, a matching filter in ON is often logically equivalent to applying it later in WHERE. A LEFT JOIN behaves differently. ON determines which right-side records are eligible to match; WHERE filters the joined results, including any null-padded rows. Placing a condition for the right table in WHERE can accidentally remove the very unmatched rows that a LEFT JOIN was intended to retain.

-- Seven left-side miners remain; only Hall 1 racks match.
SELECT m.miner_id, r.rack_name
FROM miners AS m
LEFT JOIN racks AS r
  ON m.rack_id = r.rack_id AND r.location = 'Hall 1'
ORDER BY m.miner_id;

-- Only three matching miners remain.
SELECT m.miner_id, r.rack_name
FROM miners AS m
LEFT JOIN racks AS r ON m.rack_id = r.rack_id
WHERE r.location = 'Hall 1'
ORDER BY m.miner_id;

Observed test results: the first query returns seven miners, with NULL rack fields for Hall 2 miners and unassigned miners. The second returns only IDs 1001, 1002 and 1003, three rows. SQLite's documentation explicitly distinguishes these processing stages. The WHERE conditions lesson provides the foundation for reasoning about the filter.

Counting equipment by rack

Joining from the racks table toward the miners table makes it possible to report an empty rack. Group by the rack's identity and count only the matched miner IDs. COUNT(m.miner_id) ignores NULL values; COUNT(*) counts the null-padded outer-join row as an output row. An empty Rack D therefore produces zero with the first count but one with the second.

SELECT r.rack_name,
       COUNT(m.miner_id) AS miner_count
FROM racks AS r
LEFT JOIN miners AS m
  ON m.rack_id = r.rack_id
GROUP BY r.rack_id, r.rack_name
ORDER BY r.rack_id;

Observed test result: Rack A = 2, Rack B = 1, Rack C = 2, Rack D = 0. Grouping also illustrates why a join does not automatically deduplicate parent records. A rack assigned to two miners participates in two matching pairs. Use COUNT(DISTINCT ...) only when the distinct business entity being counted is defined clearly and the additional operation is appropriate.

Parameterization, indexes, and realistic limits

When an application searches by rack location, pass the location as a bound parameter rather than concatenating untrusted input into SQL. The harness uses WHERE r.location = ? with a bound value of 'Hall 2', returning miner IDs 1005 and 1006. Placeholders differ across drivers, so use the binding syntax provided by the actual database API.

import sqlite3
connection = sqlite3.connect(":memory:")
connection.execute("PRAGMA foreign_keys = ON")
# After creating the lab schema:
hall = "Hall 2"
rows = connection.execute(
    """SELECT m.miner_id
       FROM miners AS m
       JOIN racks AS r ON m.rack_id = r.rack_id
       WHERE r.location = ?
       ORDER BY m.miner_id""",
    (hall,)
).fetchall()
# Expected: [(1005,), (1006,)]

Indexes on join keys can improve selected workloads, but their benefit depends on table sizes, cardinality, query plans, statistics and the chosen optimizer. Use EXPLAIN QUERY PLAN for SQLite and equivalent tools for other systems before claiming a measured speed improvement. Join type alone does not determine performance. Troubleshooting and assessment

  • Missing rows after joining: determine whether an INNER JOIN intentionally excludes unmatched records, whether a LEFT JOIN has a right-table predicate in WHERE, and whether the key values really match.
  • Unexpected row multiplication: check whether the relationship is one-to-many or many-to-many; do not assume the joined result has the same row count as either source table.
  • NULL surprises: use IS NULL and IS NOT NULL; = NULL does not test missing values correctly.
  • Ambiguous column: use qualified names like m.rack_id and r.rack_id rather than relying on an unqualified shared name.
  • Foreign key not enforcing: inspect PRAGMA foreign_keys on the same SQLite connection, outside an open transaction.
  • Incorrect counts: distinguish counting output rows with COUNT(*) from counting non-null matched IDs with COUNT(m.miner_id).
  • Unstable report order: add an explicit, sufficiently deterministic ORDER BY; a join does not guarantee natural row order.
  • Untrusted inputs: use parameter binding and permissions appropriate to the database; do not assemble arbitrary SQL from a request string.

Practice problems: replace the INNER JOIN with LEFT JOIN and predict the additional two records. Reverse the LEFT JOIN to identify Rack D. Rewrite the location filter first inside ON and then inside WHERE, explaining the seven-versus-three row difference. Add one additional synthetic miner to Rack B and identify which row counts change. Demonstrate the effect of COUNT(*) for an empty rack. Finally, attempt to insert an invalid rack reference and explain why foreign-key enforcement prevents it.

Answers: LEFT JOIN retains miner IDs 1004 and 1007 with missing rack values. Reversing the join reveals Rack D as unused. Restricting Hall 1 matches within ON preserves all seven left-side miners, while WHERE eliminates Hall 2 and unmatched rows, leaving three. A new Rack B assignment increases its count by one and increases the total assigned-miner count by one. COUNT(*) sees one null-padded Rack D row, while COUNT(m.miner_id) sees zero matched miner IDs. A foreign key to rack 999 is rejected when enforcement is enabled and that parent is absent.
